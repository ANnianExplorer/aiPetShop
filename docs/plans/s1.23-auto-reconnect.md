# S1.23 断线自动重连（BACKLOG B8）

- 状态：进行中
- 日期：2026-11-14
- 对应条目：`docs/BACKLOG.md` B8「前端没做自动重连」

## 1. 目标

用户在手机上聊到一半切后台、进电梯、Wi-Fi 掉一下，回来后：

1. 回答**自己接着往下长**，不用手点「重试」；
2. 已经显示的字**不会重复一遍**；
3. 重连期间界面明确显示「正在重连（第 N 次）」，而不是假装还在思考；
4. 重连彻底失败时，才回落到现有的「重试」按钮。

验收以「断线后 3 秒内自动续传，`after=<最后收到的 id>` 之后的事件不重不漏」为准。

## 2. 先摸清的底层事实（决定方案能不能成立）

原始需求写的是「断网 3s 后自动 `replayRun(afterSeq)` 续上」。动手前先核对后端行为，结论是：**只改前端做不到**。

| 事实 | 位置 | 后果 |
| --- | --- | --- |
| SSE 由请求协程直接驱动 | `app/api/routes.py` 的 `chat()` → `runner.stream()` | 客户端一断，生成器被关闭 |
| 断线即 `finish_run(CANCELLED)` | `app/runtime/runner.py` 的 `stream()` `finally` | 运行**立刻终止**，答案永远不会生成 |
| 事件日志里没有 `done` | `RedisEventStore.append` 只在 `_record` 被调用时写 | 重连只能拿到半截，`done` 永不到来 |
| `GET /agent/runs/{id}/events` 只做快照 | `routes.py::replay_run` | 即便 run 还在跑，也只返回"此刻之前"的事件 |

也就是说：**当前实现里，"断线续传"只在"服务端进程没死、客户端自己重连同一个 run"的窄场景成立；真实断网下续不上**。SPEC 4.4 第 4 条（断开即 cancelled）把这条设计钉死了。

所以本批要先把「运行的生命周期」从「HTTP 连接的生命周期」里解耦出来，前端重连才有意义。

## 3. 方案取舍

### 3.1 三个选项

| 方案 | 做法 | 代价 | 结论 |
| --- | --- | --- | --- |
| A 前端重发 | 断线后用同一 `client_message_id` 重发 `POST /agent/chat`（幂等） | 被 cancelled 的 run 只能回放半截，重发也拿不到 `done`；要改幂等语义「非成功 run 可重跑」，等于把并发双跑的窗口打开 | ❌ |
| B 运行脱离连接（**采用**） | 请求路径只负责「建 run + 转发事件」；真正执行交给后台任务，事件写事件日志；`/events` 增加 `follow=1` 长尾跟随 | 需要重构 `runner.stream` 的一处生命周期；进程被杀仍有僵死 run（属 B3） | ✅ |
| C 客户端轮询会话历史 | 断线后每 2s 拉一次消息表 | 只能拿到「最终答案」，流式体验丢失；且用户看不到进度 | ❌ |

### 3.2 采用 B 的理由

- **一句话**：谁的生命周期该长，就让谁长。答案属于 run，不属于这一次 HTTP 连接。
- 事件日志已经是唯一真相（多副本下 B 实例也能续传），`follow` 只是把「读一次」改成「读到终止为止」，不新增存储。
- 不引入消息队列、不引入 WebSocket，改动面可控（`runner` / `follow` / `routes` 三处 + 前端一个归约器）。

### 3.3 边界（明确不做）

- 不做「用户主动取消正在跑的 run」的接口（不属于 B8）；
- 不改幂等语义（I16 保持：同 key 同 run）；
- 进程被强杀导致的 `running` 僵尸 run 仍需 B3 的超时收敛，本批只在报告里重复登记。

## 4. 设计

```text
POST /agent/chat
  ├─ _prepare（请求路径内，同步）：会话 / 幂等回放 / 建 run / 首事件 route
  ├─ supervisor.spawn(_drain)   ←── 后台任务：驱动执行、把事件写进事件日志
  └─ follow_events(run_id, after=route.seq)  ←── 请求路径只做「读日志」
         │
         └─ 客户端断开：读日志的生成器被关，后台任务继续跑完 → done 落日志

GET /agent/runs/{id}/events?after=N&follow=1
  └─ follow_events(...)：先补齐存量，再轮询到终止事件 / 运行结束 / 跟随超时
```

关键不变量：

| # | 断言 |
| --- | --- |
| N1 | 关闭消费端（模拟断网）**不得**取消运行：`agent_run.status` 最终为 `succeeded`，事件日志里恰好一条 `done` |
| N2 | `follow` 从任意游标 `after` 继续，事件 `id` 严格递增、不重复、不丢 |
| N3 | `follow=0`（默认）行为与旧版完全一致（快照语义），不改变 I2/I3 的验收 |
| N4 | 幂等回放路径（同 `client_message_id`）仍走原样转发，不被后台任务接管 |
| N5 | 前端重连间隔默认 3s，最多 3 次；`after` 始终等于「已收到事件的最大 id」，保证不重复追加 |

## 7. 风险

| 风险 | 影响 | 处置 |
| --- | --- | --- |
| 进程被强杀 → run 停在 `running` | 管理端看到永不结束的运行 | 已有 B3 条目，本次不扩大范围；`run_deadline_s` 仍兜住执行时长 |
| 轮询间隔把首 token 拖慢 | 体验退化 | 首事件仍走请求路径直出，只有后续事件走 50ms 轮询；冒烟里测首 token 不变差 |
| 后台任务无人消费（客户端已走）时答案白算 | 多花 token | 这是「断线也能拿回答案」的代价；`run_deadline_s` 限制上限 |
| 多副本下 `follow` 落在另一个实例 | 读不到本地内存事件日志 | 事件日志走 Redis（S1.6 已具备），内存后端仅单副本使用 |

## 8. 落地偏差（实施后回填）

| 计划 | 实际 | 原因 |
| --- | --- | --- |
| `_prepare` + `_drain` 两段拆分 | `_drive`（原 `stream()` 整体改名，一行没改）+ `_StreamContext` 标记 + 新 `stream()` 只负责「读日志」 | 少改原逻辑 = 少引入回归；用 `ctx.replay_only` / `ctx.run_id` 区分「幂等回放」与「真跑」，比拆 `_prepare` 更省事且更好读 |
| `spawn` 在首事件之后 | **先 spawn 再 yield 首事件** | 首版先 yield 再 spawn，客户端收到 `route` 就断时 run 仍会被 `finally` 冲掉 |
| 未预见 | 修了 `storage/memory.py::finish_run` 状态不同步 | 内存版 `get_run` 返回对象本身，`finish_run` 只改 `record["status"]` → 状态永远 `running`；`follow` 靠库状态收口，这个洞必须先补 |
| 冒烟只要求"3s 内补齐" | 5 条断言（含"重连时 run 还在跑，follow 挂住等到终态"） | 只测"事后重连"测不到等待路径；改成掐线后 150ms 就重连，实测 follow 等待 656ms |
