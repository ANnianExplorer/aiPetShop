# S1.18 方案：宠物画像 `profile_snapshot`（BACKLOG C2）

- 日期：2026-11-08
- 状态：**已完成（2026-11-08）**，见 [交付报告](../reports/2026-11-08-s1.18-profile.md)
- 目标：把「已确认的长期事实」聚合成一份**带版本、带证据、可审计**的画像，供对话上下文、管理端、后续桌宠使用。
- 原则：**画像不是一段 prompt**；它由规则生成，可回放到具体事实，不接受模型自由发挥。

## 0. 为什么现在做

| 现状 | 问题 | 本轮解决 |
| --- | --- | --- |
| `memory_fact` 只有一条条 `key=value` | 对话里只能逐条念事实，说不出"这只猫挑食、对牛奶过敏、疫苗该补了"这种结论 | 规则聚合出 `traits / preferences / riskFlags / careGaps` |
| 事实会变，但没有任何快照 | 无法回答"上次的口径是什么"，管理端无法审计 | 追加式版本 + 最近 N 版可查 |
| 每次对话都重新拼事实 | 上下文长度随事实条数线性增长 | 画像摘要只注入**风险与待办**两行 |

## 1. 数据模型

`profile_snapshot`（追加式，**不覆盖**历史）：

| 列 | 类型 | 说明 |
| --- | --- | --- |
| `id` | BIGINT PK | 雪花 |
| `user_id` / `pet_id` | BIGINT | `pet_id=0` 表示"该用户不区分宠物的通用画像" |
| `version` | INT | 同一 `(user, pet)` 内自增，从 1 开始 |
| `data` | MEDIUMTEXT | 画像 JSON（见 §2） |
| `fact_count` | INT | 生成本版时用到多少条事实（对账用） |
| `confidence` | DECIMAL(3,2) | 取所用事实的加权均值，低于 0.7 的事实不参与 |
| `create_time` | DATETIME | 生成时间 |

索引：`UNIQUE (user_id, pet_id, version)`、`KEY idx_latest (user_id, pet_id, version DESC)`。
保留策略：每个 `(user, pet)` 只留最近 `PROFILE_VERSIONS_KEEP=20` 版（超出的物理删除）。

## 2. 画像内容（确定性规则，无 LLM）

```json
{
  "basics":   { "name": "Lumina", "age": "3岁", "weightKg": 4.6 },
  "traits":   { "appetite": "picky" },
  "preferences": [{ "text": "爱吃：鸡胸肉", "evidence": "memory_fact:<id>" }],
  "riskFlags": [{ "text": "对牛奶过敏", "evidence": "memory_fact:<id>" }],
  "careGaps": [{ "text": "疫苗记录是 312 天前的，建议确认是否要补种", "evidence": "memory_fact:<id>" }],
  "routine":  {},
  "evidence": [{ "key": "allergy", "value": "牛奶", "confidence": 0.95, "factId": "..." }]
}
```

规则表（每条都能指回事实）：

| 输出 | 输入 | 规则 |
| --- | --- | --- |
| `basics.name/age/weightKg` | `pet_name`/`pet_age`/`pet_weight` | 原样；`pet_weight` 解析成数字失败则只存字符串到 `basics.weightText` |
| `riskFlags` | `allergy` | 「对 X 过敏」 |
| `preferences` | `food_like` | 「爱吃：X」 |
| `traits.appetite` | `food_avoid` | 有忌口 → `picky`，否则 `normal`（缺事实不给结论） |
| `careGaps` | `vaccine` | 事实 `update_time` 距今天 > `PROFILE_VACCINE_STALE_DAYS=300` 天 → 提示补种 |
| `routine` | — | 本轮不做（需要日志/提醒数据，走 Java 工具） |

**硬约束**：没有事实支撑的字段一律**不出现**（不写 `unknown`、不猜）。

## 3. 刷新与注入

- 触发：每轮对话成功收尾后发布 `agent.profile.refresh`（key = `{user}:{pet}`）。
- 去抖：最新快照的 `create_time` 距今 < `PROFILE_REFRESH_TTL_S`（默认 300s）则跳过，避免每句话都写一版。
- 降级：队列满/未装配 → 直接跳过（画像是派生数据，缺一轮不影响回答）。
- 注入：`prepare_node` 在记忆事实之后追加**最多两行**（`风险：…`、`待办：…`），并把快照 id 写进 `run started` 日志，便于回查。

## 4. 接口

| 方法 | 路径 | 说明 |
| --- | --- | --- |
| GET | `/agent/profile/me?pet_id=` | 本人最新画像；没有则 404；`stale=true` 表示事实比快照新 |
| POST | `/agent/profile/me/rebuild?pet_id=` | 立即重算（同步，返回新版本） |
| GET | `/agent/profile/me/versions?pet_id=&limit=` | 最近 N 版（管理端 diff 用） |
| GET | `/agent/admin/profile?user_id=&pet_id=` | 管理端查看他人画像（写 `admin.access`，`scope=profile`） |

## 5. 验收（可执行）

1. `pytest tests/test_profile.py`：规则表逐条、缺事实不产出、`stale` 判定、跨用户隔离、版本自增与裁剪。
2. `pytest`：全量 ≥ 上次 183（新增用例只增不减）。
3. `ruff check .` 全绿。
4. 真机：8099 以 mysql+redis 起，`/agent/profile/me/rebuild` → 版本 1；再说一句话 → 版本 2；`versions` 返回两版；`profile_snapshot` 行数与 `fact_count` 对账。
5. 注入证据：`run started` 日志出现 `profile_version`，且 L1 请求的 system 里含「风险：」行（用 `ScriptedModel.stream_calls` 断言）。

## 6. 风险

| 风险 | 处理 |
| --- | --- |
| 规则太"硬"，画像显得简单 | 明确写进文档：本轮只做**可回放**的结论；自然语言总结留给后续版本 |
| 快照膨胀 | 保留 20 版 + 按 `(user,pet)` 唯一递增，物理删除旧版 |
| 画像过期（用户改了事实但没触发） | `stale` 字段 + 每轮对话触发刷新 + 管理端可手动 rebuild |
| 管理端看到他人画像的隐私风险 | 仅 admin、必写审计、只返回结构化摘要不返回原文 |
