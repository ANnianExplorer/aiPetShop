# S1.31 单实例容量上限扫描（C7 收尾）

- 批次：S1.31（2026-11-17 夜）
- 对应 BACKLOG：C7「压测与容量基线」剩余项——单实例上限未触到（S1.29 只扫到 20 并发）
- 状态：已完成（2026-11-17；首 token P95 口径 140 达标 / 150 超限）

## 目标

用既有 `scripts/load_baseline.py` 把单实例的容量上限扫出来：从 30 并发起，逐档加码，直到**首次出现错误或首 token P95 超过 3000ms**，给出「上一档达标 / 这一档超限」的明确边界，并记录该档的 P50/P95/P99、错误率、峰值内存与服务侧开销。

## 做法与取舍

- 固定桩模型首 token 900ms、帧间隔 20ms、每帧 4 字（与 S1.29 一致），只量服务侧管道，不引入模型网络抖动。
- 档位先 `30,40,60`，每档 60 请求、预热 1 次、逐档重启 app；若全绿再追加 `80,100,150`，直到超限或 150 并发。
- 存储用 `PET_AGENT_REPO_BACKEND=memory`、限流关闭、run sweeper 关闭（脚本既有 `app_env`），排除落库与后台任务干扰。
- 判定沿用脚本口径：错误率 ≤1%、首 token P95 ≤3000ms。
- 上限定义取「首次超限档」而不是「性能拐点」：拐点需要更细的档位和更长的采样，本轮预算不够，只作为观察项写进报告。

## 验收标准

1. `--levels 30,40,60 --requests 60` 跑完，输出真实表格（成功数、P50/P95/P99、峰值内存）。
2. 若全绿，追加更高档位，直到出现首个超限档或到 150 并发；报告写清最高达标档与首个超限档。
3. 报告贴原始命令与关键输出，注明本机配置、Python/服务版本、是否有客户端瓶颈迹象。
4. 更新 `docs/BACKLOG.md` C7（上限已给出则收尾；仍未触到则写清新的下界与下一步）、`docs/README.md` 报表、必要的根 README 数字。
5. 提交 + 附注标签 `v2.10-agent-s1.31-capacity-ceiling`，推送 `main --follow-tags`。

## 风险

- **本机即压测机**：并发升高后客户端（Python 单进程 httpx）自身可能先饱和，P95 抬升未必是服务端上限。缓解：看服务侧 `/metrics` 对账、失败形态（连接错误 vs 超时 vs 5xx）、CPU 占用，结论里如实标注。
- Windows 调度与杀软扫描会造成长尾抖动：单档样本 60 个，P95 有噪声；必要时对边界档复跑一次确认。
- 端口/残留进程：脚本逐档重启，异常退出可能留下 8098/8099 监听；跑完检查并清理。

## 不做

- L2（工具链最多 6 跳）容量与真模型长尾分布——需另配桩剧本/真实 API，记回 BACKLOG。
- 多 worker / 多实例横向扩展压测——当前部署形态是单实例，超出本轮范围。
