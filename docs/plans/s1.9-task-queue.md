## 1. 要解决的真实问题

现在 `AgentRunner.stream` 在**响应路径上**同步做这些事：

| 步骤 | 位置 | 问题 |
| --- | --- | --- |
| 记忆召回 | `runner._recall` | 每轮一次 MySQL 查询，慢时拖首字 |
| 记忆抽取落库 | `runner._observe`（`await`） | 抽取是纯规则（快），但落库与后续 LLM 抽取都会变慢 |
| 审计写入 | `ToolGateway._finish` → `audit_tool_call` | 每次工具调用一次 INSERT，失败只打日志 |
| 用量聚合 | `repo.usage_summary` | 管理端每次查询实时 `SUM`，数据量上来会慢 |

目标：**首 token 延迟不受旁路工作影响**；旁路失败可重试、可观测、可回放。

## 2. 设计

### 2.1 接口（`app/tasks/base.py`）

```python
class TaskMessage(BaseModel):
    topic: str
    key: str                # 去重键：user_id / run_id
    payload: dict[str, Any]
    attempt: int = 0

class TaskQueue(Protocol):
    async def publish(self, topic: str, key: str, payload: dict[str, Any]) -> str: ...
    async def aclose(self) -> None: ...

class TaskWorker(Protocol):
    async def run(self, stop: asyncio.Event) -> None: ...
```

- **at-least-once**：投递可能重复，消费端必须按 `key` 幂等；
- **重试**：消费失败指数退避，最多 3 次后进死信（`task_dlq` 表或 Redis list），并打 `task failed` 日志；
- **背压**：单进程内队列设上限（默认 1000），满了降级为同步执行并打 `task queue full`（宁可慢，不丢）。

### 2.2 三个实现

| 实现 | 依赖 | 用途 |
| --- | --- | --- |
| `InProcessTaskQueue` | 无（`asyncio.Queue` + 后台 worker 任务） | 单副本/测试默认 |
| `RedisTaskQueue` | 现有 Redis 5（`LPUSH` + `BRPOPLPUSH` + processing 列表） | 多副本、重启不丢；只用 5.0 已有命令，不依赖 Stream consumer group |
| `RocketMQTaskQueue` | RocketMQ broker | 企业环境；Python 端用 HTTP 代理或 `roc` 客户端 |

> 实现与初稿的差异：原计划用 `XADD` + `XREADGROUP`，落地时改用 `LPUSH`/`BRPOPLPUSH`/`LREM`——本机 Redis 是 5.0，且队列语义（先进先出 + 在途可见 + 可重投）用列表就够，少一层消费者组状态。`recover_inflight` 负责把崩溃时卡在 processing 的消息搬回主队列。

RocketMQ 的接入姿势（避免在 Python 里硬扛客户端）：

```
Python(Producer)  --HTTP-->  Java /internal/mq/publish  --rocketmq-spring-->  Broker
Python(Consumer)  <--HTTP--  Java /internal/mq/pull      （或 Java 侧直接消费写库）
```

即：**Python 只承诺 `TaskQueue` 协议，RocketMQ 由 Java 侧承载**，`rocketmq-spring-boot-starter` 是官方组件，比 Python 的 C++ 绑定稳。

### 2.3 首批迁移的三个 topic

| topic | 生产者 | 消费者 | 幂等键 |
| --- | --- | --- | --- |
| `agent.memory.observe` | `runner` 成功收尾后 | 记忆抽取 + 落库 | `(user_id, run_id)` |
| `agent.audit.tool` | `ToolGateway._finish` | 批量写 `tool_call_log` | `tool_call.id` |
| `agent.usage.rollup`（后续） | 定时 | 预聚合到 `agent_usage_daily` | `(user_id, day)` |

- **S1.9-a（可立即做，无新基础设施）**：`TaskQueue` 抽象 + `InProcessTaskQueue` + `RedisTaskQueue`，迁移 `memory.observe` 与 `audit.tool`，补契约测试与报告。

## 5. 风险

| 风险 | 处置 |
| --- | --- |
| at-least-once 导致重复写 | 所有消费者按 key 幂等（`INSERT ... ON DUPLICATE KEY UPDATE` 或先查后写） |
| 队列满/中间件挂 | 降级同步执行 + `task queue unavailable` 日志；不因为 MQ 挂了拒绝对话 |
| 记忆延迟可见（用户下一轮问，上一轮还没写完） | 抽取是纯规则、毫秒级；若换 LLM 抽取，recall 时**以 MySQL 为准并接受最终一致**，并在 SPEC 里写明 |
| RocketMQ 单机版内存参数过大 | 启动脚本 `-Xms4g` 改 256m，否则本机起不来 |
| 多副本重复消费（Redis） | `BRPOPLPUSH` 先搬到 processing，处理完才 `LREM`；进程崩了由 `recover_inflight` 搬回，代价是可能重复一次（消费者幂等兜底） |

## 6. 不做什么

- 不把 SSE 事件流换成 MQ（见 ADR-0009）；
- 不引入 Kafka（本场景没有日志型吞吐需求，多一套运维不划算）；
- 不做跨服务事务消息；
- 不在 S1.9-a 阶段改 `agent_run` 的状态机。
