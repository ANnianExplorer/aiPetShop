# S1.43 死信阈值告警（BACKLOG B4 收尾）

> 计划批次：S1.43 ｜ 短名：dlq-alert ｜ 日期：2026-11-27

## 1. 目标

让死信从「只有管理员点开页面才看得见」变成「自己会叫」：

1. 某个 topic 的死信数达到阈值时，worker 打一条 **WARNING** 结构化日志，并累加
   `pet_agent_dlq_alerts_total{topic}`；
2. `/metrics` 暴露 `pet_agent_dlq_depth{topic}`，Prometheus 可直接配告警规则；
3. 管理端与告警用的死信条数**包含无法解析的坏 payload**，不再出现
   「列表为空、实际卡着一条重放不了的消息」；
4. 同一段超阈值只告警一次；回落到阈值下再升上来会重新告警（边沿触发，不刷屏）。

## 2. 为什么现在做

BACKLOG B4 的退避重试、有界自动重投、多副本语义都已交付，唯独剩这一行：

> 死信超阈值打 WARN / 接告警通道（估算 1 天）

现状的三个具体缺口：

- `TaskWorker` 只处理消息，不观察死信总量；死信进 DLQ 后只有一条 `task dead letter`
  ERROR，没有「已经堆到阈值」的信号；
- `/metrics` 只有主队列深度 `pet_agent_queue_depth`，没有死信深度，Prometheus
  无法对死信配置告警；
- `RedisTaskQueue.dead_letters()` 会跳过解析失败的 payload，而
  `admin_tasks` 恰好用 `len(dead_letters())` 计数——坏消息越多，页面显示越少，
  与事实相反。

这是 P1 中唯一不依赖外部 broker / 真机读屏、可以在一轮内闭环的条目。

## 3. 方案取舍

| 方案 | 判定 | 理由 |
| --- | --- | --- |
| A. 每条死信立即 webhook 告警 | ✗ | 要引入 HTTP 客户端、地址与密钥配置，还要处理告警通道自身的失败重试；超出本轮边界 |
| B. 巡检时边沿触发 WARN + Prometheus gauge/counter | ✓ | 零新依赖；日志采集与 Prometheus 都是现成通道；阈值、开关都能配置 |
| C. 每轮巡检都打一条 WARN | ✗ | 死信长期不处理会变成日志刷屏，反而淹没真正的新故障 |
| D. 计数继续用 `len(dead_letters())` | ✗ | 坏 payload 被静默跳过，恰好把最需要告警的情况漏掉 |
| E. 给 `TaskQueue` 增加 `dead_letter_count()`，Redis 用 `LLEN` | ✓ | O(1)、包含坏消息；两套实现同签名，管理端与告警共用一份事实 |

结论：**B + D 的反面 + E**。告警通道 = 结构化 WARN（日志采集）+ Prometheus
`pet_agent_dlq_depth`（抓取告警），不新增网络依赖。

## 4. 设计

```text
TaskWorker._sweep_loop（默认 60s 一轮）
  ├─ retry_due()                     退避到期搬回
  ├─ sweep()                         回收卡死在途
  ├─ redrive_dead_letters()          可选：有界自动重投
  └─ _check_dlq_alerts()             ← 本轮新增
        for topic in topics:
          count = queue.dead_letter_count(topic)   # Redis: LLEN / 内存: len
          if threshold <= 0:                       跳过（关闭）
          elif count >= threshold and not active:
              WARNING task dlq threshold exceeded  {topic, dead_letters, threshold}
              metrics.inc(pet_agent_dlq_alerts_total{topic})
              active.add(topic)
          elif count < threshold and active:
              INFO task dlq below threshold        {topic, dead_letters, threshold}
              active.discard(topic)

GET /metrics
  ├─ pet_agent_queue_depth{topic}        （已有）
  └─ pet_agent_dlq_depth{topic}          ← 新增 gauge，来自 dead_letter_count()

GET /agent/admin/tasks
  └─ dead_letters = dead_letter_count(topic)   ← 不再 len(dead_letters())
```

不变量：

| # | 断言 |
| --- | --- |
| K1 | `dead_letter_count()` 与死信实际条数一致；Redis 下包含无法解析的坏 payload |
| K2 | 首次达到阈值（`count >= threshold`）只打一条 WARNING，字段含 topic / 条数 / 阈值 |
| K3 | 持续超阈值不重复告警；只有回落到阈值下再升上来才再次告警 |
| K4 | 回落时打一条 INFO 复位日志，之后可重新告警 |
| K5 | `threshold = 0` 关闭告警；`task_sweep_interval_s <= 0` 时巡检不跑，告警也不跑 |
| K6 | `/metrics` 的 `pet_agent_dlq_depth{topic}` 与实际死信数一致，且不含用户内容 |
| K7 | 多 topic 的告警状态互相独立，一个 topic 复位不影响另一个 |

边界说明：

- 告警是**采样**：巡检间隔内「回落到阈值下又立刻升回」可能观察不到，按边沿语义处理；
- 多副本各自持有进程内 `active` 集合，阈值穿越时每个副本各打一条 WARN；
  Prometheus 用 `max by (topic)` 聚合即可，不追求全局恰好一次；
- 坏 payload 会被 `replay_dead_letter()` 留在 DLQ（防止污染主队列），因此管理端
  计数可能暂时降不下来——这是「需要人工清理」的真实信号，不是计数错误。

## 5. 实施步骤

1. `app/tasks/base.py`：协议增加 `dead_letter_count(topic) -> int`，写清与
   `dead_letters()` 的差异（计数含坏消息、列表用于展示/重放）。
2. `app/tasks/redis_queue.py`：`LLEN {prefix}:{topic}:dlq`。
3. `app/tasks/inprocess.py`：`len(self._dlq.get(topic, ()))`。
4. `app/config.py`：新增 `task_dlq_alert_threshold: int = Field(default=1, ge=0)`。
5. `app/tasks/worker.py`：
   - 构造参数 `dlq_alert_threshold: int = 1` 与进程内 `_dlq_alert_active: set[str]`；
   - `_sweep_loop` 在每轮重试/回收/重投之后调用 `_check_dlq_alerts()`；
   - 达到阈值打 WARNING + 指标，回落打 INFO 并复位。
6. `app/core/metrics.py`：新增 `DLQ_DEPTH` / `DLQ_ALERTS` 常量。
7. `app/api/app.py`：把 `settings.task_dlq_alert_threshold` 传给 worker。
8. `app/api/routes.py`：
   - `admin_tasks` 改用 `dead_letter_count()`；
   - `/metrics` 追加 `# TYPE pet_agent_dlq_depth gauge` 与每个 topic 的值。
9. 测试：
   - `tests/test_task_queue.py`：计数契约（两实现）、Redis 坏 payload 计数、
     告警只打一次、回落后重新告警、`threshold=0` 关闭、按 topic 独立；
   - `tests/test_metrics.py`：`/metrics` 含死信深度 gauge 且值与死信数一致。
10. 文档：`docs/spec/agent-runtime-api.md` §6.10、`docs/README.md` 计划/报告表、
    `docs/BACKLOG.md` B4 行、根 README 与 `backend-agent/README.md` 的配置/测试数。

## 7. 风险

| 风险 | 影响 | 处置 |
| --- | --- | --- |
| 阈值默认 1 让死信立刻告警 | 运维收到预期内的 WARN | 死信本身即异常；需要静默可设 `0`，或在日志侧按级别过滤 |
| 巡检关闭导致告警不跑 | `task_sweep_interval_s=0` 时无告警 | 在 SPEC 与 README 写明；需要告警就保留巡检 |
| 多副本重复 WARN | 同一时刻多条告警 | 按 topic 聚合；WARN 只用于触发，最终以 gauge 为准 |
| 坏 payload 无法通过管理端重放清除 | 计数长期不降 | 真实反映「需人工清理」；报告里列为已知缺口，不在本轮擅自删数据 |
| 每次巡检多一次 `LLEN`/内存计数 | 可忽略 | 默认 60s 一次、topic 数固定为 3 |
