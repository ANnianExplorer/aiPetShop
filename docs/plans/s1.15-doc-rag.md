# S1.15 计划：A3 文档问答（文件 / 图片 / 视频）

- 状态：已完成（2026-11-08）— 见 [REPORT](../reports/2026-11-08-s1.15-doc-rag.md)
- 目标：把 `docs/BACKLOG.md` 的 A3 从"没有表、没有解析、没有向量"做到**可上传、可解析、可检索、可引用**，Agent 能在对话里回答"我传的疫苗本上写了什么"
- 前置：S1.14 已交付（三端构建、后端 27 单测、卫生债清零）

---

## 1. 为什么先做这个

| 现状 | 影响 |
|---|---|
| `doc_file` / `doc_chunk` 两张表不存在 | 没有任何"用户资料"概念，Agent 只能查业务表 |
| 无解析链路 | 用户上传的疫苗本、化验单、聊天截图无法进入模型上下文 |
| 无向量/检索 | 即使有文本，也只能整篇塞进 prompt，几千字就爆预算 |

产品侧的说法：App 里"一句话问出疫苗记录"目前只覆盖结构化记录；**用户自己拍的照片、从医院拿到的 PDF 目前完全用不上**——这是"像真实养宠助手"和"查表工具"的分水岭。

## 2. 范围（本轮做什么、不做什么）

### 做

| 能力 | 实现 |
|---|---|
| 上传 | `POST /agent/documents`（multipart），落本地对象目录，按 `(user_id, sha256)` 去重 |
| 解析 | 文本类（`txt/md/csv/json/log`）直读；`pdf` 用 `pypdf` 按页抽文本；图片/视频走**可插拔 OCR/抽帧适配器**，二进制缺失时明确标记 `unsupported` 并给出原因 |
| 切分 | 按段落/句子切成 600–900 字、重叠 120 字的块，保留 `locator`（`page=3`、`t=93s`、`offset=1200`） |
| 嵌入 | 默认 `hash` 本地嵌入（确定性、零网络，256 维 char-ngram 哈希）；可切 `openai` 兼容 `/embeddings` |
| 检索 | 余弦相似度，按 `user_id`（可选 `pet_id`）过滤后暴力排序；单次最多取 2000 块，返回 `top_k=5` |
| 引用 | `doc:<file_id>#page=3` 形式，前端可回跳 |
| 工具 | `search_docs(query, pet_id?, top_k?)` 注册进工具目录，纯只读 |
| 异步 | 复用 S1.9 的 `TaskQueue`：`agent.doc.ingest` topic；`TASK_BACKEND=off` 时同步解析 |

### 不做（明确写进 BACKLOG）

- **视频转写**：本机没有 `ffmpeg`/ASR，视频只能抽帧 OCR（也要 `ffmpeg`）；需要先装二进制，代码已留适配器
- **图片 OCR**：本机没有 `tesseract`；适配器已实现（调用 CLI），装了就生效
- **向量库**：MySQL 8 没有向量类型，本轮用"过滤 + 内存余弦"，上限 2000 块；规模化再换 pgvector/Qdrant（ADR-0010 记录）
- 文档问答的**评测集**：本轮只做 5 条冒烟，正式评测放 S2

## 3. 数据模型（`backend/sql/v2.16-doc-rag.sql`）

```sql
doc_file(id BIGINT PK, user_id BIGINT, pet_id BIGINT NULL, name VARCHAR(255),
         mime VARCHAR(128), size_bytes INT, sha256 CHAR(64), storage_key VARCHAR(512),
         status TINYINT,   -- 0 queued 1 parsing 2 ready 3 failed 4 unsupported
         error VARCHAR(512), chunk_count INT, create_time DATETIME, is_delete TINYINT,
         UNIQUE KEY uk_user_sha (user_id, sha256))
doc_chunk(id BIGINT PK, file_id BIGINT, user_id BIGINT, chunk_index INT,
          locator VARCHAR(64), content TEXT, token_hint INT, embedding MEDIUMTEXT,
          dim INT, create_time DATETIME, KEY idx_file (file_id), KEY idx_user (user_id))
```

要点：
- `embedding` 存 JSON 浮点数组（MySQL 8 无向量类型），`dim` 便于换模型后识别旧向量
- `uk_user_sha` 让同一用户重复上传同一文件直接复用，不重复计费
- `status` 用状态机而不是布尔，解析失败能带原因

## 4. 关键设计决策

### 4.1 为什么嵌入默认用 hash 而不是"调模型"

- 本机/离线环境必须有可用路径；调远端 embedding 会让"上传即失败"
- hash 嵌入（char 3-gram → 256 维 signed hashing）对中文短文本可召回，虽然语义能力弱，但**可解释、可测试、零成本**
- `Embedder` 是协议：`PET_AGENT_EMBED_BACKEND=openai` 时换成真模型，索引里 `dim` 会标出新旧不一致

### 4.2 为什么解析要独立成"适配器 + 能力探测"

`ffmpeg`/`tesseract` 不是 Python 依赖，装不装取决于部署环境。做法：启动/首次使用时探测二进制，能力矩阵写进 `/agent/documents/capabilities`，用户看到"图片暂不支持：服务器未安装 OCR"，而不是静默失败或瞎编内容。

### 4.3 为什么复用 TaskQueue 而不是新起 Celery

S1.9 已经有 `publish/receive/ack/recover`、死信、启动补偿。文档解析正是"投递-消费-重试"模型：大 PDF 解析十几秒，不能卡住上传请求。

### 4.4 检索的租户隔离

`search_docs` 的 `user_id` 由工具网关注入（模型不能传），仓储层 SQL 强制 `WHERE user_id = ?`；`pet_id` 只做进一步过滤。测试用"两个用户各传一份同名文件"验证不串。

## 5. 验收标准（可执行）

| # | 验收 | 命令/现象 |
|---|---|---|
| 1 | 上传文本 → 解析完成 | `POST /agent/documents` → `status=2`、`chunk_count>0` |
| 2 | 重复上传同文件 | 返回同一 `document_id`，`chunk_count` 不变 |
| 3 | PDF 按页可引用 | 上传 2 页 PDF，检索命中返回 `locator="page=1"` |
| 4 | 检索排序正确 | 与问题相关的块排第一（测试用固定语料断言） |
| 5 | 租户隔离 | 用户 B 检索不到用户 A 的块 |
| 6 | 工具接入 | L2 对话命中 `search_docs`，`done.citations[0].kind=="doc"` |
| 7 | 不支持的类型 | 上传 `.mp4`（无 ffmpeg）→ `415` + `unsupported_reason` 可读 |
| 8 | 删除 | `DELETE` 后检索不到，`doc_chunk` 级联清理 |
| 9 | 单测 | `pytest` 全绿（新增 ≥ 12 例） |
| 10 | 真机 | MySQL 版跑通 1–8（`REPO_BACKEND=mysql`） |

## 6. 风险

| 风险 | 处置 |
|---|---|
| 大文件把内存打爆 | 上传限制 20MB；PDF 页数上限 200；解析在旁路线程 |
| hash 嵌入召回差 | 明确写"v1 是字面召回"，语义检索随 `openai` 后端启用 |
| 向量存 JSON 体积大 | 256 维 ≈ 3KB/块；1000 块 ≈ 3MB，可接受；后续换向量库 |
| 敏感内容入库 | 文档按 `user_id` 隔离；删除是真删（`doc_chunk` 直删） |
