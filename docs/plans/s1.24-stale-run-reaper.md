# S1.24 僵尸 run 收敛（BACKLOG B3 剩余部分）

> 计划批次：S1.24 ｜ 短名：stale-run-reaper ｜ 日期：2026-11-14

## 1. 目标

`agent_run` 里停在 `running`、但对应进程早就没了的行，由巡检收敛成 `cancelled`，
并写一句人能看懂的原因，管理端能直接看到。**只收敛开始时间超过阈值的行**，绝不碰活 run。

## 2. 为什么现在做

S1.23 把「运行」从「连接」上摘下来之后，`finally` 能兜住正常结束、异常和客户端断开，
但兜不住**进程直接消失**（`kill -9`、OOM、机器重启）。这种 run：

- 管理端看起来像「任务卡住了」，永远不结束；
- 前端重连时 `follow` 会一直等到 `run_follow_timeout_s` 才放弃，用户看到的是「一直转圈」；
- `B3` 在 2026-11-08 只交付了任务队列的在途回收，这一半一直挂着。

## 3. 方案取舍

| 方案 | 判定 | 理由 |
| --- | --- | --- |
| A. 每个 run 写心跳列，巡检看心跳 | ✗ | 要加列 + 每次 delta 都 UPDATE，写放大明显；而运行本来就受 `run_deadline_s` 兜底，开始时间足够判断 |
| B. 按 `create_time < now - stale_run_timeout_s` 收敛 | ✓ | 零额外写入；判据单一，管理端可解释；阈值必须大于 `run_deadline_s` |
| C. 只在启动时扫一次 | ✗ | 长稳进程里照样会攒僵尸（例如单个 worker 线程被杀但进程还在） |

采取 **B + 定时巡检（启动扫一次 + 默认 60s 一轮）**。

## 4. 设计

```text
lifespan 启动
  ├─ sweep_once(repo, timeout_s=stale_run_timeout_s)     ← 收尸：上一轮进程留下的
  └─ supervisor.spawn(janitor_loop, name="run-janitor")  ← 长稳期间的定时巡检
        └─ repo.sweep_stale_runs(older_than_s, error=…)
              ├─ SELECT id FROM agent_run WHERE status='running' AND create_time < … LIMIT 200
              └─ UPDATE … WHERE id=%s AND status='running'   ← 条件更新，多副本只有一个能改到
```

不变量：

| # | 断言 |
| --- | --- |
| J1 | 开始时间未超阈值的 run 不被动（不误杀在跑的任务） |
| J2 | 已终态的 run 不被动（条件更新 + 内存版跳过） |
| J3 | 收敛后 `status=cancelled`、`error` 是人话、`latency_ms` 是真实耗时 |
| J4 | 重复巡检是空操作（幂等；多副本下不会重复处理） |
| J5 | 单轮失败（数据库抖动）不让巡检循环退出 |
| J6 | 阈值必须大于 `run_deadline_s`（配置护栏，测试兜底） |

## 5. 实施步骤

1. `storage/base.py`：加 `sweep_stale_runs(older_than_s, *, error) -> list[str]` 契约（含为什么用开始时间、为什么必须条件更新）。
2. `storage/memory.py`：按 `record["created"]` 判龄，走 `finish_run(CANCELLED, …, error)`；撞上真实收尾就 `ValueError` 认输。
3. `storage/mysql.py`：先 `SELECT` 候选，再逐条条件 `UPDATE`（`rowcount` 决定是否算收敛），`latency_ms` 用 `TIMESTAMPDIFF` 现算。
4. `app/runtime/janitor.py`：`stale_run_error()` 生成人话原因、`sweep_once()`、`janitor_loop()`（异常只记日志）。
5. `app/config.py`：`stale_run_timeout_s=900`、`run_sweep_interval_s=60`（0 = 只在启动扫一次）。
6. `app/api/app.py`：lifespan 先扫一次再启动循环（用 S1.23 的 `RunSupervisor` 托管，退出时自然收掉）。
7. 测试：`tests/test_janitor.py` 六个用例 + `tests/test_repository_contract.py` 一条「刚起来的 run 不被碰」（内存/MySQL 两套都跑）。

## 7. 风险

| 风险 | 影响 | 处置 |
| --- | --- | --- |
| 阈值小于运行超时 | 误杀正常运行 | 默认 900s ≫ `run_deadline_s=60s`，并有测试断言 |
| 巡检和真实收尾撞车 | 双向报错 | 双方都是条件更新；输的一方跳过，不抛给用户 |
| 主从延迟下读到旧状态 | 重复收敛 | 条件更新在写库端判定，读旧不影响正确性 |
| 大批僵尸一次收敛 | 长事务 | 单轮上限 200 条，剩下的下一轮继续 |
