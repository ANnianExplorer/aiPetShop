# S1.16 运维与数据自主（P1 / B3 · B5 · B7）

> 状态：进行中（2026-11-08）
> 目标：把「出问题能看见、卡住能自愈、数据能自己删」这三件事补上，不引入新基础设施。

## 0. 为什么是这三项

`docs/BACKLOG.md` 里 P1 共 8 条，其中三条不需要新中间件、但直接影响线上可运维性：

| 编号 | 现状 | 不做的后果 |
| --- | --- | --- |
| B3 | `:processing` 只在进程启动时 `recover_inflight` 回收 | 消费者卡死/被杀而不重启时，消息永远卡在 `:processing`，记忆与审计静默丢失 |
| B5 | 只有结构化日志与 `/readyz`，没有数值指标 | 无法回答「现在 QPS 多少、429 占比多少、队列积压多少」，只能翻日志 |
| B7 | 记忆只增不删、只能逐条 `GET` 看 | 用户无法行使删除权，画错了也只能看不能改 |

B1（RocketMQ）需要 broker、B2（多副本）需要多实例、B6（管理端页面）偏 UI，均不在本轮。

## 1. B3：在途消息可见性超时回收

**语义**（对齐 SQS 的 visibility timeout，不追求 exactly-once）：

- 取用消息时把它登记到 `{prefix}:{topic}:claimed`（ZSET，score = 取用时刻），同时在 `:processing` 保留原文；
- ack / nack 时同时清 `:processing` 与 `claimed`；
- 后台巡检每 `task_sweep_interval_s` 秒扫一次：`claimed` 中超过 `task_visible_timeout_s` 的条目，若仍能在 `:processing` 里找到就搬回主队列，并且 **attempt + 1**（防止「消费者一取就崩」形成无限循环，超过 `max_attempts` 最终进死信）；
- 巡检搬回时打 `task inflight swept` 日志（topic / swept / timeout）。

**边界**：

- 真正的慢任务仍可能被执行两次——消费端按 `key` / `event_id` 幂等（ADR-0009 第 4 条），这是刻意接受的 at-least-once；
- 单副本下 `:processing` 为空即无成本；多副本下巡检只做「搬回」，不做 kill。

**验收**

- `sweep` 对内存实现返回 0（无在途状态，不假装能扫）；
- Redis 实现：造一条「已取未 ack」消息，把 `visible_timeout_s` 设 0.01 → `sweep` 返回 1、主队列 1 条、`attempt` 变 2、`claimed` 清空；
- ack 之后再 sweep 不会把已消费的消息搬回；
- `TaskWorker` 启动后巡检任务会被取消（`stop()` 不残留 task）。

## 2. B5：最小 Prometheus 指标

**指标**（全部进程内累计，无外部依赖）：

| 指标 | 类型 | 标签 |
| --- | --- | --- |
| `pet_agent_http_requests_total` | counter | `method` `path` `status` |
| `pet_agent_http_request_duration_seconds` | summary | `method` `path`（`_sum` / `_count`） |
| `pet_agent_runs_total` | counter | `route` `status` |
| `pet_agent_tool_calls_total` | counter | `tool` `ok` |
| `pet_agent_queue_depth` | gauge | `topic` |
| `pet_agent_tokens_total` | counter | `direction`（`prompt` / `completion`） |

**取数位置**：

- HTTP：`RequestContextMiddleware` 里已有状态码与耗时，顺手 +1 / observe；
- run / tool / token：`AgentRunner` 与 `ToolGateway` 收尾处；
- 队列深度：`/metrics` 渲染时同步读 `depth(topic)`（Redis 有成本，但只发生在抓取时）。

**边界**：`path` 用路由模板（`/agent/documents/{document_id}`），不是原始 URL，避免高基数；不采集任何用户内容；`/metrics` 不加鉴权（Prometheus 侧控制网段），在 SPEC 里写明。

**验收**：请求一次 `/healthz` 后 `pet_agent_http_requests_total{...status="200"} ≥ 1`；跑一轮 L1 对话后 `runs_total` 与 `tokens_total` 有值；`/metrics` 输出可被 `text/plain; version=0.0.4` 解析（按行正则断言即可）。

## 3. B7：记忆可删、可导出

| 接口 | 语义 |
| --- | --- |
| `DELETE /agent/memory/me?key=&pet_id=` | 删除本人一条事实；不存在返回 404；物理删除即可（`memory_fact` 无审计要求） |
| `GET /agent/memory/me/export` | 导出本人全部事实（含 `key`/`label`/`value`/`confidence`/`update_time`），`{"version":1,"exported_at":...,"facts":[...]}` |

- 仓储层新增 `delete_memory_fact(user_id, pet_id, key) -> bool`；MySQL 用 `DELETE ... WHERE user_id AND pet_id AND fact_key`（`pet_id` 用 0 表示无宠物维度，与 `uk_user_pet_key` 一致）；
- 只允许操作本人数据（`user_id` 从身份解析，不接受参数）；管理端仍走 `/agent/admin/memory`（只读）。

**验收**：A 写入事实 → A 能导出、能删除 → 删除后再导出为空、再删 404；B 删 A 的 key 不影响 A（B 自己 404）。

## 5. 风险

| 风险 | 处理 |
| --- | --- |
| 巡检误搬「正在跑但很慢」的任务 | 默认 120s 可见性超时，文档写明按最慢 handler 调；消费端幂等兜底 |
| `/metrics` 被外部扫到泄露信息 | 只有计数与耗时，无 id/内容；生产建议网关侧限制 |
| 记忆物理删除不可恢复 | 属产品预期（用户行使删除权）；导出接口给用户留底 |
