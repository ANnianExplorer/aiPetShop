# S1.38 MySQL/Redis 备份与恢复演练（BACKLOG D7）

- 状态：已完成（2026-11-22）
- 关联：`docs/BACKLOG.md` D7、`backend-agent/scripts/backup_restore.py`、`backend-agent/tests/test_backup_restore.py`
- 批次：S1.38

## 1. 目标

当前 MySQL 与 Redis 都没有脚本化备份，也没有任何一次被证明能恢复的演练。本切片交付一条可重复执行的运维链路：

1. **备份**：一次命令同时导出 MySQL（`mysqldump --single-transaction`）与 Redis（默认 `BGSAVE` 后拷贝服务端 RDB），生成带 sha256 的清单 `manifest.json`；
2. **离线校验**：不连数据库也能验证「文件在、哈希对、gzip 可解、SQL 表数对、RDB 魔数对」，CI/交接前可跑；
3. **恢复演练**：MySQL 恢复到临时库、Redis 用临时端口加载 RDB，逐表比对行数与 `CHECKSUM TABLE`、逐 DB 比对键数量与键名哈希，最后强制清理临时库/临时实例；
4. **真实证据**：在本机 MySQL 8.0.29 + Redis 5.0.14.1 上跑一次完整 drill，报告贴真实输出。

## 2. 现状与取舍

- **不做通用备份平台**：只服务本仓库的 Agent 侧存储（`PET_AGENT_MYSQL_DSN` / `PET_AGENT_REDIS_URL`），不引入新依赖、不接对象存储。
- **MySQL 用 CLI 而非 `pymysql` 导数据**：`mysqldump` 处理转义、字符集、触发器/存储过程更可靠；Python 只负责哈希、清单与比对。
- **默认只备 `petlumina` 单库**：`mysqldump` 不带 `--databases`，因此不会写入 `CREATE DATABASE`/`USE`，恢复目标由脚本显式指定为临时库，避免误覆盖生产库。
- **恢复目标必须隔离**：临时库名固定前缀 `petlumina_drill_` + UTC 时间戳 + 随机后缀；Redis 一定起新进程、新端口、新目录，绝不碰线上 6379。
- **清单不含口令**：DSN/URL 只保留 `user:***@host:port/db`；Redis 只存 DB 键数量与键名 sha256，不存键名本身（本机存在 `satoken:*`）。
- **校验口径**：MySQL 行数用 `COUNT(*)`、内容用 `CHECKSUM TABLE`；Redis 用 `INFO keyspace` 的 keys/expires + 排序后键名 sha256。
- **Redis 备份用服务端 BGSAVE 拷贝**：本机 Windows 版 `redis-cli --rdb` 以文本模式写盘（每个 `0x0A` 变成 `0x0D 0x0A`），导出的 RDB 校验必失败。默认发 `BGSAVE`、轮询 `INFO persistence` 到 `rdb_bgsave_in_progress:0` 且 `rdb_last_bgsave_status:ok`，再拷 `CONFIG GET dir`/`dbfilename` 指向的文件；`--rdb` 只作回退，且必须过 `redis-check-rdb`。manifest 的 `method` 记录实际路径。
- **已知竞态**：备份期间若有写入，行数/校验和可能与清单漂移；drill 会明确列出差异表，不把竞态伪装成通过。Redis 键有 TTL，备份后隔太久再 drill 可能出现「键过期」差异，报告需写明。

## 3. 实现

### 3.1 命令

```bash
cd backend-agent
.venv\Scripts\python -m scripts.backup_restore backup --out D:\backups\petlumina --label nightly
.venv\Scripts\python -m scripts.backup_restore verify --backup D:\backups\petlumina\20261122T150000Z-nightly
.venv\Scripts\python -m scripts.backup_restore drill  --backup D:\backups\petlumina\20261122T150000Z-nightly
```

- `backup`：`--mysql-dsn` / `--redis-url` 缺省读 `PET_AGENT_MYSQL_DSN` / `PET_AGENT_REDIS_URL`；两者都为空则报错。
- `verify`：纯离线，任何一项失败退出码 1。
- `drill`：对清单里存在的组件做恢复校验，写 `drill-report.json`，失败退出码 1；即使失败也清理临时资源。

### 3.2 产物布局

```text
<out>/<UTC 时间戳>-<label>/
  manifest.json
  mysql.sql.gz
  redis.rdb
  drill-report.json   # 仅 drill 后生成
```

`manifest.json`（schema_version=1）关键字段：

```json
{
  "schema_version": 1,
  "created_at": "2026-11-22T15:00:00Z",
  "label": "nightly",
  "mysql": {
    "database": "petlumina",
    "server_version": "8.0.29",
    "dsn": "mysql://root:***@127.0.0.1:3306/petlumina",
    "dump": {"file": "mysql.sql.gz", "bytes": 123, "sha256": "..."},
    "tables": [{"name": "agent_run", "rows": 12, "checksum": 1057712515}]
  },
  "redis": {
    "url": "redis://127.0.0.1:6379/0",
    "server_version": "5.0.14.1",
    "rdb": {"file": "redis.rdb", "bytes": 1142, "sha256": "..."},
    "method": "bgsave-copy",
    "keyspace": {"db0": {"keys": 4, "expires": 4, "keys_sha256": "..."}}
  }
}
```

### 3.3 模块划分（`scripts/backup_restore.py`）

- `MySqlConn` / `RedisConn`：解析 DSN、脱敏、构造客户端；
- `backup_mysql`：导 dump、查版本、逐表行数/校验和、gzip、清单；
- `backup_redis`：`BGSAVE` 拷贝（或 `--rdb` 回退）、`INFO keyspace`、逐 DB 键名哈希；
- `verify_backup`：离线校验（纯函数 + 文件检查），返回逐项 `checks`；
- `restore_mysql`：建临时库 → 导入 → 比对 → 删除；
- `restore_redis`：临时端口起 `redis-server` → 比对 → `SHUTDOWN NOSAVE` → 删目录；
- `compare_mysql` / `compare_redis`：纯函数，单测主战场。

### 3.4 安全与清理

- 口令只通过子进程环境变量 `MYSQL_PWD` / `REDISCLI_AUTH` 传递，不进程命令行、不落盘、不打印；
- 临时 SQL 解压到工作目录（系统临时目录不可写时回退仓库内 `.tmp-drill`），`finally` 删除；
- MySQL `DROP DATABASE` 只对本次 `CREATE` 成功的临时库执行；
- Redis 临时实例 `SHUTDOWN NOSAVE`，进程未退再 `terminate`/`kill`，目录 `rmtree`。

## 4. 验收标准

1. `backup` 在本机真库产出 `manifest.json` + `mysql.sql.gz` + `redis.rdb`，清单中 grep 不到本机口令；dump 内 `CREATE TABLE` 数 = 清单表数。
2. `verify` 对完整备份返回 0；篡改任意字节、删除文件、改坏 gzip、RDB 魔数错误均返回 1 并指出具体项。
3. `drill` 在本机真 MySQL/Redis 上恢复成功：27 张表行数与 `CHECKSUM TABLE` 全等，Redis 4 个键/键名哈希全等；临时库与临时实例在结束后不存在。
4. 新增单测覆盖：DSN 脱敏、临时库名安全、清单读写、篡改检测、表差异、Redis 键哈希；`pytest` 全量通过。
5. `ruff check app tests scripts` 全绿（scripts 也在检查范围时显式跑一次）。
6. 文档同步：`docs/README.md` 的 PLAN/REPORT 表、`docs/BACKLOG.md` D7 与统计、根 `README.md` 的测试/文档数字。

## 5. 风险

- **竞态**：备份期间业务写入会导致 drill 行数/校验和差异；脚本报差异而非自动忽略，夜间低峰执行可降低概率。
- **CHECKSUM TABLE 引擎差异**：MyISAM/分区表可能返回 `NULL` 或不稳定；脚本对 `NULL` 跳过内容比对并记录，不伪造通过。
- **Redis TTL**：备份到 drill 之间键过期会造成差异；本切片要求备份后尽快 drill，报告写明。
- **Windows 路径/编码**：`redis-cli --rdb`、`mysqldump` 路径含空格时用参数列表传递；子进程输出按 UTF-8/GBK 兜底解码。
- **Windows `redis-cli --rdb` 不可用**：本机 5.0.14 版把二进制 RDB 当文本写（实测 `redis-check-rdb` 报 `Unknown RDB string encoding type 58`）；默认走 `BGSAVE` 拷贝，只有服务端目录不可读时才回退 `--rdb`，并用 `redis-check-rdb` 拒绝坏文件。
- **权限**：MySQL 需要 `CREATE/DROP DATABASE` 与 `SELECT`；Redis 需要 `SYNC`/`SHUTDOWN`。权限不足时脚本给出明确失败项，不静默跳过。
- **大库耗时**：本机 1.63MB 秒级；生产大库应改用 `--single-transaction` + 压缩流与独立备份盘，本切片不承诺容量指标。

## 6. 非目标

- 不做定时调度、保留策略/轮转、异地存储、加密备份；
- 不做 Java 业务侧 `backend/` 的独立备份（同一 `petlumina` 库已被覆盖）；
- 不做增量备份、binlog 恢复、Redis AOF；
- 不改任何业务代码与 API。
