# S1.29 单实例容量基线：给「20 并发」一个真实数字（BACKLOG C7）

- 状态：进行中
- 日期：2026-11-16
- 对应条目：BACKLOG C7「压测与容量基线缺失」
- 预算：单轮夜间维护（约 2 小时）

## 1. 问题

C7 的验收写得很直白：「记录 20 并发 SSE 的首 token P95 / 错误率 / 峰值内存，并给出单实例上限」。
现在这三样都没有：

- 仓库里只有**冒烟**脚本（`scripts/e2e_smoke.py`、`scripts/reconnect_smoke.py`），它们全串行、各发 1 个请求，只能回答「通不通」，回答不了「能扛多少」；
- `docs/spec/agent-runtime-api.md` 里的性能段是**单发**实测（模型首 token P50 约 929ms），并发下会发生什么没有任何数据；
- 没有数字就没法扩容、没法设告警阈值、没法判断某次「用户说卡」是模型慢还是我们自己慢。

这条不是锦上添花：**没有容量基线的 SSE 服务，第一次真上量就是靠用户反馈当监控**。

## 2. 目标

1. 交付可复现的压测脚本 `scripts/load_baseline.py`：一条命令起「桩模型 + 被测服务」，分级并发扫一遍，输出真实数字；
2. 逐档记录：**首 token P50/P95/P99**、全程耗时 P95、**错误率**（含 SSE 正常收尾率）、**app 进程峰值工作集**、`/metrics` 增量对账；
3. 给出单实例上限的**判定口径**（错误率与首 token P95 双阈值），并明确写出它是「在桩模型节奏下」的上限；
4. 顺手修掉压测的**噪声源**：`tests/stub_llm.py` 在 async 生成器里用 `time.sleep(0.01)` 阻塞事件循环，并发下会把 N 个请求串成一条线——不修它，测出来的是桩的天花板，不是服务的天花板；
5. 全程零新增依赖（不引 locust / psutil），Windows 本机与 Linux 都能跑。

## 3. 方案与取舍

### 3.1 为什么是「两个子进程 + 父进程当客户端」

复用 `scripts/e2e_smoke.py` 的形态，但把「客户端」放在父进程：

```
父进程（压测客户端，httpx.AsyncClient，真 TCP）
  ├── 子进程 A: uvicorn tests.stub_llm:app   （可配首 token 延迟，仿真真实模型节奏）
  └── 子进程 B: uvicorn app.main:app         （每个并发档重启一次，内存峰值可归因）
```

- **不用进程内 uvicorn**（`scripts/reconnect_smoke.py` 的做法）：内存峰值要读被测进程，同进程里读到的会被压测客户端自己抬高；
- **每档重启 app**：`PeakWorkingSetSize` 是进程生命周期高水位，不重启就分不清「这一档涨了」还是「上一档留下的」；
- **桩进程只起一次**：它是无状态的，重启没意义，还会把「模型侧」的变化混进对比；
- **真 TCP、真 HTTP**：`httpx` 走真实 socket，不做 ASGI 内部直调，这样连 uvicorn 的解析/写回开销一起量进去。

### 3.2 为什么给桩加「首 token 延迟」而不是直接量空转

如果不延迟，`tests/stub_llm.py` 回一句 20 字的闲聊只要几毫秒，测出来的就是 uvicorn 的纯调度上限——一个**乐观到没有参考价值**的数字。给桩配一个与线上实测同量级的首 token 延迟（默认 900ms，对齐 `docs/spec/agent-runtime-api.md` 里模型 P50 929ms），压测结果就能拆成两部分：

```
客户端首 token P50 ≈ 桩的首 token 延迟 + 服务侧额外开销
```

这样报告里能直接说「服务侧额外开销 P50 = X ms」，而不是含糊的「首 token 1s」。

**已知偏差（写清，不装）**：桩不是真模型——真模型在并发下的排队、限流、长尾都没模拟；所以本基线量的是**Agent 服务自身的调度/内存上限**，不是「20 个真人同时问 DeepSeek 会怎样」。

### 3.3 压测口径

| 项 | 取值 | 理由 |
|---|---|---|
| 请求 | `POST /agent/chat`，`message=你好`（L1） | L1 只走一次模型往返，链路最短，最能把服务自身开销暴露出来；L2 的耗时主要被工具调用支配 |
| 认证 | `auth_mode=header` + `Authorization: Bearer <token>` + `X-User-Id` | 不依赖 stub_java，少一个进程、少一次 `/auth/current` 往返，减少噪声 |
| 限流 | `PET_AGENT_RATE_LIMIT_ENABLED=false` | 量的是容量不是配额；默认 20 次/分钟会让第二档全变 429 |
| 仓储 | `repo_backend=memory` | 本基线不测 MySQL；每档重启进程，状态天然干净 |
| 每请求一个用户 | `X-User-Id: load<档位>-<序号>` | 避免玩家维度串扰（历史/记忆互相污染） |
| 首 token 定义 | 第一个 `event: delta` 到达的时刻 | 与 App 真实渲染时机一致；`route` 事件在模型调用之前就发了，量它没有意义 |
| 成功 | 收到 `event: done` 且中途无 `event: error` | 只看 HTTP 200 会漏掉「流里报错但状态码已是 200」 |

### 3.4 上限判定

- 错误率 > 1% → 该档「超上限」；
- 首 token P95 > 3000ms（= 桩延迟的 3 倍多）→ 该档「超上限」；
- 两阈值都可 `--threshold-*` 覆盖，写进报告时一起注明。

判定只影响报告里的「判定」列，**不影响退出码**：超上限是本轮要交付的结论，不是脚本失败。

### 3.5 内存怎么量

Windows 用 `psapi!GetProcessMemoryInfo` 读 `PeakWorkingSetSize`（`ctypes`，零依赖），非 Windows 回退 `/proc/<pid>/status` 的 `VmHWM`。读两次：

- `peak_startup`：就绪后再读，代表「空载 + 已 import」；
- `peak_after`：压完这一档再读，代表「该档峰值」。

报告同时给两个数，避免把启动开销算进容量。

### 3.6 拒绝的选项

- **locust / k6**：新依赖 + 新工具链，为一个 200 行的脚本不值；而且 k6 在 Windows 上要另外装。
- **psutil**：唯一用途是读内存，`ctypes` 十行搞定，不值得加运行时依赖（本项目 agent 侧一直保持零第三方运维依赖）。
- **改 `app/` 里的任何生产代码**：本轮目标是**测量**，不是优化。发现瓶颈就写进 BACKLOG，不在没有基线的情况下瞎调。
- **在仓库里留压测产物**：按 `AGENTS.md` 约定，日志落 `%TEMP%`，JSON/报告数据用 `.tmp-` 前缀，提交前删净。

## 5. 风险

| 风险 | 影响 | 缓解 |
|---|---|---|
| 桩模型不是真模型 | 结论不能直接当「线上 20 并发」用 | 报告标题与结论都写明前提；给出「服务侧额外开销」这一定义不含糊的数字 |
| 客户端与两个服务同机抢 CPU | 高并发档的数字偏悲观 | 报告注明同机；用「每档重启 + 同机比例」看趋势而非绝对值 |
| Windows 计时精度约 15ms | 低延迟档的 P50 有量化误差 | 首 token 延迟设为 900ms 量级，量化误差占比 <2%；全程耗时用 `perf_counter` |
| `PeakWorkingSetSize` 含启动 import | 峰值看起来偏大 | 同时给 `peak_startup`，报告里明确「含启动」 |
| 高并发档把本机打满 | 影响同一台机器上其他进程 | 默认最高 20 并发；`--levels` 需显式指定才往上扫 |
