# S1.31 单实例容量上限扫描（C7 收尾）

- 日期：2026-11-17
- 对应 BACKLOG：C7「压测与容量基线」剩余项——单实例上限未触到
- 状态：已完成（首 token P95 口径；L2/真模型仍未量）

## 结论

**首 token P95 口径下，单实例最后达标档是 140 并发（P95 2994ms），150 并发连续两次越过 3000ms 阈值（3100ms / 3202ms）。**

- 安全建议：生产按 **100 并发**规划（P95 2004ms，约 33% 余量），不要贴着 140 跑。
- 若改为看**全程 P95**，140 并发已经到 3235ms、150 到 3331/3410ms——即「首 token 达标」不等于「整条流达标」，容量口径必须写清楚。
- 150 档错误率仍为 0%，`/agent/chat` 301/301、runs 301 成功 / 0 失败；上限表现为**长尾延迟**，不是报错或 OOM。
- 内存不是瓶颈：启动 90MB，压测峰值 146MB（+55MB），150 档与 140 档基本持平。

## 做了什么

1. **修掉压测协议缺陷**：`run_level` 只创建 `requests` 个任务，`Semaphore(level)` 的真实并发是 `min(level, requests)`。本轮第一次跑 `--levels 80,100,150,200,300 --requests 60` 时，这些档位实际都只有 60 并发，数字全部失真（都「达标」且几乎一样）。
   - 在 `parse_args` 增加校验：`--requests` 必须 ≥ 最大档位，否则直接 `parser.error` 退出 2，避免再把「没跑到目标并发」写成「上限未触到」。
2. **修掉结论渲染的非单调 bug**：原逻辑在「40 超限、60 又达标」时会写「上一档 60 并发达标」（荒谬）。现在检测到更高档位达标时输出「结果非单调，疑似抖动，需复测该档」。
3. 用修正后的协议重扫：每档 300 请求（≥ 2 倍并发），逐档重启 app、预热 1 次、冷却 0.5s；桩模型首 token 900ms / 帧间隔 20ms / 每帧 4 字。
4. 补 4 条单测：请求数不足的配置被拒、边界相等放行、非单调结论、单调结论的上一档命名。

### 噪声与异常记录

- 第一次 60 请求版的 40 档出现 P50 2974ms / P95 3344ms 的尖峰；同配置复跑 40 档为 1668/1726ms，300 请求版为 1272/1369ms——判为机器抖动，不写进上表。
- 120/130/140 三档的 P50 非单调（1779 → 2180 → 1866），P95 却单调贴线，说明本机同跑压测端/桩/服务时噪声主要落在调度上，结论只认 P95 趋势。
- 全程 P95 在 140 档已 3235ms > 3000ms；阈值仍按脚本既有的「首 token P95」口径判定，报告同时给出全程值，避免只看首 token 误判。

## 已知局限（下一轮）

1. **同机压测**：客户端、桩模型、被测服务抢同一台机器的 CPU；150 档的 P95 抬升有多少来自压测端，尚未分离。要定服务端硬上限，应换 k6/分布式压测端，或把桩放到另一台机器。
2. **只量 L1 闲聊**：L2 工具链（最多 6 跳）与真实模型长尾未量，容量结论只覆盖单轮 SSE 管道。
3. **阈值口径**：首 token P95 ≤ 3000ms 是脚本默认值，不是业务 SLO；上线前应按真实 SLO 重算安全并发。
4. 140 档 P95 2994ms 仅比阈值低 6ms，属于统计上的「贴线达标」，不适合当作运行水位。
