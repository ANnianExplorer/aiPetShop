## 2. 量的是什么（口径先定死，免得数字好看但没用）

- **首 token** = SSE 里第一个 `event: delta`，不是 HTTP 首字节。审核口令：L1 路径 = `route → prepare → END`，之后 `runner` 才
  `async for chunk in model.stream(...)` 发 `delta`（`app/runtime/runner.py:319-322`），所以首 token 延迟 ≈ 模型首字延迟 + 服务侧开销。
- **成功** = 收到 `event: done` 且期间没有 `event: error`；**错误率** = 失败数 / 总请求数。
- **每档重启 app 进程**：否则上一档的内存峰值会带到下一档，增量就没法归因。
- **桩给 900ms 固定首 token 延迟**：好把「服务自身开销」从端到端里减出来（900ms 是刻意选的，比真实 deepseek 首字慢，偏保守）。
- **每请求一个 `X-User-Id`**：避开限流器把热请求串到同一个桶上；同时把限流关掉（`PET_AGENT_RATE_LIMIT_ENABLED=false`），
  本切片量的是**服务容量**，不是限流阈值。
- **峰值内存**读 `PeakWorkingSetSize`（Windows）/ `VmHWM`（Linux），且**取整棵进程树的最大值**——本机 venv 的 `python.exe`
  是个几 MB 的启动器，真跑 uvicorn 的是它的子进程，只量 `Popen.pid` 会得到 3MB 这种假数字（详见 §6）。
- 判定阈值：错误率 ≤ 1% 且首 token P95 ≤ 3000ms → 达标；超阈值只影响表格判定，**不影响退出码**（这脚本是量尺不是闸门）。
- **子进程日志**：`default_log_dir()` 先真的写一次探针再决定目录。不能用 `tempfile.gettempdir()`——本机（DSH 沙箱）Python
  子进程写 `%TEMP%` 直接 `PermissionError: [Errno 13]`，而 `gettempdir()` 会**静默回退到当前目录**，日志就撒进仓库了
  （第一版就是这么把 11 个 `petlumina-load-*.log` 写进 `backend-agent/` 的）。现在退到仓库内 `.tmp-load-logs/`（`.tmp-*` 已 gitignore）。

```text
## 结论

- 上限：扫到的最高档 20 并发仍达标，单实例上限未被触到。
- 服务侧额外开销（首 token P50 − 桩延迟）：+251ms @ 20 并发；全程 P95 1300ms。
- 峰值工作集：97MB（含启动 90MB，压测增量 +7MB）@ 20 并发。
- 对账：/agent/chat 计数 +41、runs 成功 +41/失败 +0；期望 41（40 计时 + 1 热身）→ 一致。

```

`+41` 对账不是凑数：每档有 1 次热身请求（也是真请求，也进 `/agent/chat` 与 `runs` 计数），所以期望值是 `40 + 1`；
`/metrics` 里的 `pet_agent_runs_total{status="succeeded"}` 与 `pet_agent_http_requests_total{path="/agent/chat"}`
两个口径独立收敛到同一个数，说明**没有请求被静默吞掉**。

## 4. 怎么读这些数字

- **吞吐没有被串行化**：首 token P50 从 959ms（1 并发）爬到 1151ms（20 并发），只多了 192ms（+20%）；如果是单线程串行，
  20 并发下 P50 应该飞到 20 秒级。这条和「改 `asyncio.sleep` 后桩不再阻塞事件循环」是一起验的（见 §7 第 3 条）。
- **服务侧开销是真开销**：3000ms 阈值下，900ms 桩延迟之外的部分从 59ms（1 并发 P95 986 − 900）涨到 301ms（20 并发 P95 1201 − 900）。
  也就是说在 20 并发时，一个请求的首 token 里有约 300ms 花在 Agent 自己的解析、身份、路由、日志与 SSE 组装上。
- **内存几乎不随并发涨**：90MB 启动 → 97MB（20 并发），增量 7MB 里还包含 41 个 run 的事件日志与 message 存储（memory 仓储）。
  换 MySQL + Redis 事件流后增量会更高，但**曲线是平的**这点不会变——没有按连接数线性分配的内存。
- **上限在哪仍然未知**：20 并发全绿只能说明「20 并发可承载」。要写「单实例上限 ≈ N」，得继续往上扫到出现失败或 P95 抬头为止，
  本机两小时预算内没做（见 §6）。

## 6. 已知缺口与风险（不美化）

1. **没扫到上限**，所以 BACKLOG 的验收项「给出单实例上限」只完成了一半：给的是「20 并发可承载 + 该点的延迟/错误率/内存」，
   不是「上限 = N」。补法很便宜：`--levels 30,40,60 --requests 60`，出现错误或 P95 > 3000ms 的那档就是上限。
2. **同机压测**：压测客户端、桩、被测服务抢同一个 CPU，数字偏悲观；但**偏悲观是我们想要的保守方向**。
3. **桩不是真模型**：真实 deepseek 的首字延迟分布长尾比 900ms 固定值重得多，真机数字必须单独量（这也是为什么把桩延迟做成参数而不是写死）。
4. **只量了 L1**：L1 是「一次模型往返 + 流式吐字」的最短路径。L2 带工具调用（图里 `agent ↔ tools` 最多 6 跳，`max_tool_hops=6`），
   每跳一次模型往返 + 一次 Java 调用，**首 token 与总时长都会明显更差**，本轮的 20 并发结论不能直接推广到 L2。
5. **memory 仓储 + 限流关闭**：换成 MySQL 仓储或开限流（默认 20/分钟/用户）后，同样的并发会先在限流处被挡。数据面的容量另说。
6. **单实例 = 单进程**：没测多 worker（`uvicorn --workers N`）；进程模型一变，内存曲线要重测。
7. **Windows 峰值口径**：`PeakWorkingSetSize` 含共享页，和 Linux `VmHWM` 不完全等价，跨平台不要把 97MB 直接对比。
8. **进程树取值**：为了绕开 venv 的瘦启动器，取的是整棵树下最大值（深度 ≤ 3）。若某天 app 又派生出长期驻留的子进程（如 worker 池），
   这个数字会变成「最胖的那个进程」而不是「总和」。
9. **脚本不自带清理**：进程停止是 `terminate → 15s → kill`，若被硬杀（Ctrl+C 两次），8098/8099 端口可能残留，下次跑前要先清端口。

## 7. 过程记录（三次真失败，如实写）

1. **桩没有 `/healthz`**：首跑 `RuntimeError: http://127.0.0.1:54718 在 30s 内没就绪（最后一次：HTTP 404 {'detail': 'Not Found'}）`。
   桩只实现了 `/v1/chat/completions`，没有健康检查端点。改成 `wait_ready(..., path="/docs")` 用 FastAPI 自带的文档页探活，
   不去为了压测给桩加生产语义的端点。
2. **`ctypes.wintypes.c_long` 不存在**：`AttributeError: module 'ctypes.wintypes' has no attribute 'c_long'`（Toolhelp32 结构体里的
   `pcPriClassBase`）。改 `ctypes.c_long` 后过。
3. **峰值只报 3MB**：单独量 `Popen.pid` 量到的是 venv 的瘦启动器（`tasklist` 里 3,404 K），真跑 uvicorn 的是它的子进程（探针量到 50.7MB）。
   改成遍历进程树取最大值后，1 并发就报 90MB。**这条是这轮最值钱的发现**：否则报告里会写「20 并发只用 3MB」这种一眼假的数字。
4. **日志撒进仓库**：第一版用 `tempfile.gettempdir()` 当日志目录，跑完仓库里多出 11 个 `petlumina-load-*.log`。
   探针查明本机 Python 子进程写 `%TEMP%` 会 `PermissionError: [Errno 13] Permission denied`，而 `gettempdir()` 不报错、
   直接回退到 cwd。改成逐个试 `TEMP`/`TMP`/`TMPDIR` 并**真写一次探针**，都不行才退 `.tmp-load-logs/`（gitignore 覆盖）。
   交付前把仓库里那 11 个文件删干净了，`git status` 只剩预期改动。

另：中途 `ruff` 报过 `F811 Redefinition of unused 'peak_working_set_mb'`（改动过程中留下了重复定义），删掉旧定义后全绿；
删完复跑了 `pytest`（244 通过 + 1 跳过）与短档压测（`11/0` 对账一致）确认没弄坏。
