# S1.23 断线自动重连（BACKLOG B8）

- 日期：2026-11-14
- 批次：`S1.23`（短名 `auto-reconnect`）
- 方案：[plans/s1.23-auto-reconnect.md](../plans/s1.23-auto-reconnect.md)
- 标签：`v2.10-agent-s1.23-auto-reconnect`
- 范围：`backend-agent`（运行生命周期）+ `pet-lumina-app`（重连器）+ SPEC v1.13

## 1. 目标

手机切网络、进电梯、地铁过隧道——SSE 连接断掉以后，答案还能自己接着长：用户不用点重试、不用重发消息、已经看到的内容不重复。

验收标准（与 BACKLOG B8 一致）：断网 3s 后自动续上，且不重复追加已收到内容。

## 2. 结论：只改前端做不到

开工前先核对后端，三处源码直接否掉了"纯前端方案"：

| 事实 | 位置 |
| --- | --- |
| `chat()` 把 `runner.stream()` 的生成器直接当响应体，连接的存活期 = run 的存活期 | `backend-agent/app/api/routes.py`（`POST /agent/chat` 与 `replay` 两个入口） |
| 生成器 `finally` 在非终态时把 run 置 `cancelled`，注释原文"客户端断开 / 任务被取消：run 不能永远停在 running" | `backend-agent/app/runtime/runner.py`（`stream()` 的 `finally`） |
| SPEC 4.4 第 4 条当时明确规定"客户端断开时服务端把 run 置 cancelled" | `docs/spec/agent-runtime-api.md` |

也就是说：断网瞬间 run 就死了，事件日志里永远不会出现 `done`，`GET /agent/runs/{id}/events` 只能给半截——前端无论怎么重试都接不上"同一轮"。

方案取舍：A 前端重发 ✗（`cancelled` 拿不到 done；改幂等语义又会开并发双跑窗口）；B 运行脱离连接 ✓；C 客户端轮询历史 ✗（丢流式，体验退化）。

## 3. 改了什么

后端（`backend-agent`）：

| 文件 | 改动 |
| --- | --- |
| `app/runtime/supervisor.py`（新） | `RunSupervisor.spawn/_on_done/aclose/running`：把 run 的驱动任务托管到进程，任务崩了记 ERROR 而不是静默消失 |
| `app/runtime/follow.py`（新） | `follow_events(log, repo, run_id, after, poll_s, idle_timeout_s)`：按 seq 逐条吐事件，遇 `done`/`error`、库状态非 `running`、或超时收工 |
| `app/runtime/runner.py` | `stream()` 拆成 `_drive()`（原逻辑，一行没动）+ 新的 `stream()`（先 spawn 再交付首事件，然后只 `follow_events`）；`_drain()` 负责把生成器跑干、finally 关干净 |
| `app/api/routes.py` | `GET /agent/runs/{id}/events` 增 `follow=1`（挂到终态）；缺省仍是快照语义，v1.12 行为不变 |
| `app/api/app.py` | 装配 `RunSupervisor`，lifespan `finally` 先 `await supervisor.aclose()` 再关 worker |
| `app/config.py` | `run_follow_timeout_s=90.0`、`run_follow_poll_s=0.05` |
| `app/storage/memory.py` | 修真实缺陷：`finish_run` 只改了 `record["status"]`，而 `get_run` 返回的是 `record["run"]` 对象本身 → 内存版状态永远停在 `running`（MySQL 版每行重建，天然一致，所以这个洞一直没暴露） |

前端（`pet-lumina-app`）：

| 文件 | 改动 |
| --- | --- |
| `src/utils/resilientChat.ts`（新） | `streamChatResilient(payload, hooks, options)`：断线后拿 `run_id + 已收最大 id` 去 `?after=N&follow=1`，按 `[3s,3s,6s]` 重连；`open/replay/sleep` 可注入，测试不需要真等 9 秒 |
| `src/views/chat/ChatView.vue` | 换成重连版；新增链路状态（`live/reconnecting`）与"正在重连（第 N 次）"提示条；重连期间清掉旧错误、桌宠回到"想事情" |
| `src/locales/{zh-CN,en-US,ja-JP}.json` | 新增 `chat.reconnecting` |

文档：SPEC 升 v1.13（4.4 第 4 条改写、§5 增 `follow` 参数与三个结束条件、I40–I42）；BACKLOG B8 结项；`docs/README.md` 索引同步。

### 5.4 顺带修正的两个坑

1. **`spawn` 必须在 `yield first` 之前**（原实现先交付 `route` 再托管）→ 客户端收到 `route` 就断时，run 还会被 `finally` 冲掉。窗口虽小但不是零。
2. **`follow=1` 的结束条件不能只看日志** → 事件日志有 TTL/容量上限，`done` 可能被裁掉；所以"库状态已非 `running` 且日志无新事件"才收工。

## 6. 已知风险与未做

| 风险 | 影响 | 处置 |
| --- | --- | --- |
| 进程被 `kill -9` | run 停在 `running`（僵尸），前端续传会等满 `run_follow_timeout_s` 后放弃 | 归 BACKLOG B3 剩余部分（僵死 run 收敛），本轮未动 |
| 后台白算 token | 用户断开后 run 照跑，计费照旧 | 已知取舍：目标是"接回来是同一轮"，取消接口另立需求 |
| 单实例内存 | `RunSupervisor` 与事件日志都在进程内 | 多副本已由 Redis 事件日志 + B2 的共享幂等覆盖；本轮的 supervisor 不跨进程（run 归属启动它的那个实例） |
| 重连窗口 | 只重试 3 次（4 秒内），超时仍回落到"重试"按钮 | 与验收标准一致；后续可按网络类型动态调 |

本轮**没做**：主动取消接口、前端 e2e（C9）、压测（C7）。

## 7. 下次建议

1. **B3 剩余的"僵死 run 收敛"**：现在 disconnect 不再取消 run，强杀进程留下的 `running` 会比以前更常见，`run_follow_timeout_s` 到期只能让客户端放弃，服务端仍需要一个按 `create_time` 收敛的巡检。
2. 前端 e2e（C9）可以把"对话中途断网"作为第四条用例——用 Playwright 的 `route.abort()` 掐 SSE 最接近真实场景。
3. 真机 Chrome `navigator.onLine` 事件可以替代固定 3s 首等：在线事件一来就立刻重连，离线时展示"等待网络"。
