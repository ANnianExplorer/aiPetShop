# S1.24 僵尸 run 收敛（BACKLOG B3 收尾）

> 日期：2026-11-14 ｜ 批次：S1.24 ｜ 短名：stale-run-reaper
> 计划：[`docs/plans/s1.24-stale-run-reaper.md`](../plans/s1.24-stale-run-reaper.md)

## 1. 目标

`agent_run` 里停在 `running`、但对应进程早就没了的行，由巡检收敛成 `cancelled` 并写明原因；
**不碰活 run**，多副本下也只收敛一次。

## 2. 为什么做这条

S1.23 把 run 从 HTTP 连接里拆出来之后，`finally` 兜住了正常结束、异常、客户端断开三种收尾，
但兜不住**进程直接消失**（`kill -9` / OOM / 机器重启）。这类 run 会：

- 永远停在 `running`，管理端像「任务卡死」；
- 让前端 `follow` 一直等到 `run_follow_timeout_s` 才放弃（用户看到无穷转圈）。

BACKLOG 里 B3 在 2026-11-08 只交付了任务队列的在途回收，这一半一直挂着，本轮收掉。

## 3. 改了什么（7 个文件）

| 文件 | 改动 |

| `app/runtime/janitor.py`（新） | `stale_run_error()` 生成「运行超过 N 分钟没有收尾（进程可能被强杀），已由巡检标记为已取消」、`sweep_once()`、`janitor_loop()`（单轮异常只记日志，循环不死） |
| `app/config.py` | `stale_run_timeout_s=900`（15 分钟）、`run_sweep_interval_s=60`（0 = 只在启动扫一次） |
| `app/api/app.py` | lifespan 里先 `sweep_once()` 收尸，再用 S1.23 的 `RunSupervisor` 托管 `janitor_loop`（退出时随 supervisor 一起收掉） |
| `tests/test_janitor.py`（新）+ `tests/test_repository_contract.py` | 6 + 1 条用例 |

## 6. 过程记录（失败与修正，如实写）

1. 首次 ruff 4 条：`app.py` 导入顺序（I001）、`janitor.py` 多余的 `int()` 包裹（RUF046）、

## 7. 已知风险

| 风险 | 说明 |
| --- | --- |
| 阈值拍错会误杀 | 默认 900s ≫ `run_deadline_s=60s`；J6 用测试锁住「阈值必须更大」 |
| 巡检与真实收尾撞车 | 两边都是条件更新/条件 `UPDATE`，输的一方跳过，`ValueError` 不外抛 |
| 主从延迟读到旧状态 | 收敛判定在写库端（`WHERE status='running'`），读旧只影响候选集，不影响正确性 |
| 大批僵尸一次扫不完 | 单轮 200 条上限，剩余下一轮继续；不会长事务 |
| 内存仓储靠 `record["created"]` | 仅测试/本地使用；MySQL 版用库时间，不受本机时钟漂移影响 |
