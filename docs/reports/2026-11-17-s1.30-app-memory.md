## 2. 为什么是「按范围 N+1 次请求」

后端契约里 `GET /agent/memory/me` 的 `pet_id` **为空 ≠ 全部**，而是「不带宠物维度」的那一类事实
（`docs/spec/agent-runtime-api.md` §6.1、`backend-agent/app/api/routes.py:270`）。要展示全部，只能对
「通用 + 每只宠物」各拉一次，客户端合并：

- 复用既有契约，零后端改动，不碰已绿的契约测试；
- `Promise.allSettled` 并发，单范围失败不影响其它范围；页面提示「部分分组加载失败」；
- 每范围 `limit=50`（契约上限）；
- 代价是请求数随宠物数线性增长（通常 ≤ 3 只）。宠物很多时应由后端提供聚合接口，已写进 §4。

导出同理：服务端 export 也是按范围的，客户端把各范围结果装进
`{version:1, exported_at, scopes:[{pet_id, pet_name, facts}]}`。**这是客户端聚合，不是服务端单文件的逐字节结果**，
换服务端 all 导出时可无缝替换。

删除后的即时性：`TASK_BACKEND=memory|redis` 写入是最终一致的，删除成功后只做本地移除、**不自动重拉**，
避免「刚删完又出现」；重新进入页面时以服务端为准。

## 4. 已知缺口与风险（不美化）

1. **没做真机浏览器点击**：本轮没有可用的浏览器会话，页面可达性只由「路由 + 菜单 + 组件测试 + 构建产物」证明，
   `dist/assets/MyMemory-*.js` 确实产出。真机验收建议下次用 Playwright（BACKLOG C9）补一条。
2. **N+1 请求**：宠物数线性放大请求数；≥6 只宠物时应改后端聚合接口，届时删掉 `Promise.allSettled` 分支即可。
3. **导出是客户端聚合**：格式与服务端单范围导出不同，已在 §2 与方案中写明；跨版本兼容无保证（`version:1` 为客户端自有）。
4. **最终一致**：删除后马上退出再进入，可能看到旧值（Redis/memory 仓储路径），属既有契约行为，页面未做轮询。
5. **`limit=50` 截断**：单范围事实超过 50 条时列表只显示前 50，导出仍走服务端 `limit=200`；分页未做。
6. **`dist/` 入库**：本轮重新构建导致 38 个旧 asset 删除 / 41 个新增 / `index.html` 修改，diff 很大但都是构建产物；这是为了让 GitHub Pages 同步生效。

## 5. 过程记录（真实失败）

1. **`vue-tsc` 首跑红**：
   `src/views/profile/MyMemory.vue(120,46): error TS2339: Property 'reason' does not exist on type 'PromiseSettledResult<AgentMemoryFact[]>'.`
   `PromiseSettledResult` 是联合类型，直接读 `.reason` 不合法。改为 `isRejected` 类型守卫后再
   `settled.filter(isRejected)`，`EXIT=0`。**没有用 `as any` 绕过**。
2. **jsdom 没有 `URL.createObjectURL`**：下载逻辑第一版写在组件里，组件测试直接抛
   `TypeError: URL.createObjectURL is not a function`。抽到 `utils/download.ts` 并在测试里 mock 该模块，
   组件测试只断言「调用了导出、文件名与内容正确」。
3. **`tmp` 目录**：本轮所有日志都写 `%TEMP%`（pwsh 重定向可用），仓库内没有留下临时文件。
