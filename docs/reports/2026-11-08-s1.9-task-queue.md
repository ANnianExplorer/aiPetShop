## 3. 真实缺陷

| # | 现象 | 根因 | 处置 |
| --- | --- | --- | --- |
| D1 | `p1_smoke` 第二次跑就 7/9 失败 | 脚本用固定 `token-7007`，真机 MySQL 里上一轮的事实与用量还在；限流账号被上一轮打满 | 每次运行用时间戳生成新账号；限流单独账号；记忆断言前轮询 |
| D2 | `dead_letters()` 在内存实现是同步、在 Redis 实现是 async | 两个实现签名不一致，调用方得记得加 `await` | 统一为 async，测试加 `_wait_until_async` |
| D3 | 开启队列后 `p1_smoke` 的"记忆已落库"偶发失败 | 记忆走旁路，写入是最终一致 | 脚本轮询到可见再断言；SPEC 6.1 写明一致性语义 |
| D4 | `pytest` 出现 12 条 `PytestUnraisableExceptionWarning: Exception ignored in: <function Connection.__del__>` | 契约测试的 `repo` fixture 只造不关，MySQL 连接池挂在已关闭的事件循环上 | 改成 `async def` + `yield` + `finally: await aclose()`；复跑 **134 passed（0 warnings）** |
| D5 | `Warning: 'VALUES function' is deprecated` | `memory_fact` 的 upsert 用了 MySQL 8.0.20 起弃用的 `VALUES(col)` | 改成行别名写法 `INSERT ... VALUES (...) AS new ON DUPLICATE KEY UPDATE fact_value=new.fact_value, confidence=GREATEST(memory_fact.confidence,new.confidence)`，真机契约用例通过 |

> 另有一次排查结论：`job_kill` 只杀 pwsh 壳，python 子进程仍占 8099，导致"改了代码但测的是旧进程"。固定动作用 `Get-NetTCPConnection -LocalPort 8099 | Stop-Process -Force`。

## 5. 设计决策

1. **默认 `off`**：行为与 S1.8 完全一致，生产显式打开；避免"升级即变异步"。
2. **队列满退回同步**：宁可慢也不丢；只有 `TaskQueueFull` 才降级，其他异常照常抛。
3. **幂等放在消费者**：记忆按 `(user, pet, key)` upsert；审计用消息 id 作品牌键（`INSERT IGNORE`）。
4. **列表而非 Stream**：Redis 5.0 场景下 `BRPOPLPUSH` 已满足"在途可见 + 可恢复"，少一层消费者组状态。
5. **RocketMQ 放 Java 侧**（ADR-0009）：Python 只承诺 `TaskQueue` 协议。

## 6. 已知缺口

1. RocketMQ 实现未做（需 broker；本机无 Docker、无二进制）——`docs/plans/s1.9-task-queue.md` §4 已写明 S1.9-b。
2. 死信只是堆在 Redis 列表里，没有重放接口与告警。
3. `recover_inflight` 目前是手动调用，未挂在启动流程里。
4. 队列容量与消费并发没有压测数据。
5. 记忆最终一致只做到"秒级"，没有写入版本号，读侧无法判断新旧。

## 7. 复现

```powershell
cd backend-agent
$env:PET_AGENT_TEST_MYSQL_DSN = "mysql://root:<本机口令>@127.0.0.1:3306/petlumina"
.\.venv\Scripts\python -m pytest
.\.venv\Scripts\python -m scripts.e2e_smoke
.\.venv\Scripts\python -m scripts.p1_smoke
```

> 服务端需带 `TASK_BACKEND=redis`（或 `memory`）启动才能覆盖到队列路径；`off` 时上述冒烟仍然通过，但走的是同步分支。
