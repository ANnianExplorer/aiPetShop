## 1. 结论

交付 `backend-agent/scripts/backup_restore.py` 一条命令三件事：

1. `backup`：`mysqldump --single-transaction` 导出 `petlumina`，Redis 走服务端 `BGSAVE` 后拷贝 RDB，产出 `manifest.json`（sha256、逐表行数/`CHECKSUM TABLE`、Redis 键数量/键名哈希，口令脱敏）；
2. `verify`：纯离线校验文件存在、哈希、gzip 可解、dump 内 `CREATE TABLE` 数、RDB 魔数，篡改即退出 1；
3. `drill`：MySQL 恢复进临时库 `petlumina_drill_<UTC>_<rand>` 逐表比对后删除，Redis 起临时端口/临时目录加载 RDB 比对后关闭，写 `drill-report.json`。

本机真机 drill 结果：**MySQL 27/27 张表一致（28419 ms），Redis 1/1 个 DB、4 个键一致（1774 ms）**，临时库与临时实例均已清理。未改 Java / App 代码，`mvn test`、App 三件套本轮不重复冒充。

## 4. 调试中抓到的真问题

1. **`gzip.GzipFile.fileno()` 给的是压缩文件 fd**：drill 首版把 gzip 字节直接喂给 `mysql`，报 `ERROR at line 1: Unknown command '\x12'`；改成先解压到工作目录再导入。
2. **redis-py 8.1.0 默认 RESP3**：连本机 Redis 5.0.14 报 `unknown command 'HELLO'`；固定 `protocol=2`。
3. **Windows 版 `redis-cli --rdb` 以文本模式写盘**：导出 1142 字节却落成 1145 字节，每个 `0x0A` 变 `0x0D 0x0A`，`redis-check-rdb` 报 `Unknown RDB string encoding type 58`；改为 `BGSAVE` 后拷贝服务端 RDB，`--rdb` 仅回退且必须过校验。
4. **DSH 下 Python 写 `%TEMP%` 被拒**：`PermissionError: [WinError 5]`；备份/工作目录改为仓库内 `.tmp-` 前缀，跑完清理。

## 5. 未覆盖与风险

- **MySQL 契约变体未跑**：未设 `PET_AGENT_TEST_MYSQL_DSN`，跳过 1 项；drill 已用真库覆盖恢复链路，但仓储契约的 MySQL 分支仍未在本轮执行。
- **备份是明文全量**：清单不含口令，但 dump/RDB 内是业务数据（含 `satoken:*`），未加密、未做异地/保留策略；本切片只证明「可备可恢复」。
- **BGSAVE 拷贝依赖服务端目录可读**：Redis 与本脚本不同机/容器时需回退 `--rdb`，而本机 Windows 版 `--rdb` 不可用；跨机场景要改用 `redis-check-rdb` 兼容的客户端或服务端导出。
- **TTL 竞态**：Redis 键带过期时间，备份后隔太久 drill 会出现键数差异；脚本报差异不伪造通过。
- **未做定时调度**：仍是手动命令；夜间低峰执行、保留轮转、告警均不在本切片。
