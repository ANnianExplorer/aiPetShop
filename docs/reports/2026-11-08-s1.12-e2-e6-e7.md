## 4. 过程中遇到的问题

| # | 现象 | 处置 |
| --- | --- | --- |
| D1 | 迁移脚本执行报 `(1093) You can't specify target table 'n' for update in FROM clause` | `DELETE ... WHERE ... IN (SELECT id FROM (SELECT id FROM notification WHERE user_id=0) t)`，用派生表绕开 MySQL 自引用限制 |

| D3 | 通知表无已发布广播，E2 无从验证 | 插两条验收数据（广播 `900000000000000001`、admin 个人 `900000000000000002`），验证完保留在本地库、不进迁移脚本 |

## 5. 已知缺口

1. `notification_read` 只在本地 MySQL 跑过；生产库需手工执行 `v2.13-notification-read.sql`（脚本本身幂等：`CREATE IF NOT EXISTS` + `INSERT IGNORE` + `DELETE`）。
2. 旧"已读副本"迁移只在**零广播**的库上跑过，真实历史数据量大时需先备份再跑。
3. E7 只覆盖了 `NOTIFICATION` 与 `GLOBAL` 异常映射；其余 Controller 的 `throw new BusinessException` 走同一 handler，但没有逐个接口回归。
4. 前端错误提示只验证了编译；未在浏览器里逐个触发 400/401/404 看文案。
5. `sortField` 白名单只接了三个 Service；其它列表仍按默认排序（未接的传参会被忽略，但不是回归）。

## 6. 结论

**可交付。** 三个卫生债都有真机证据：未读 2→1→0 且列表不重复、排序升/降序对称且注入字段被丢弃、错误码 400/401/404 与 body 一致。剩余风险集中在"生产库迁移"与"未逐个接口回归"，已列入 BACKLOG 与本节第 5 条。
