## 结论

C9 的三条验收链路已在真实浏览器（系统 Edge + Playwright）跑通：

1. App：登录 → 对话 → 看到引用「疫苗记录」→ 点击回跳 `#/log/7001`；
2. 管理端：管理员登录 → 会话列表 → 会话详情（对话流、引用、运行轨迹）；
3. App：第二次提问触发 429 → 显示「请求太频繁，请稍后再试」+ 重试按钮。

最终 e2e **3 passed（22.2s）**，runner 退出码 0；App `vue-tsc`/`vitest`/`build` 与后端 `pytest` 均通过。首次运行暴露了管理端 hash 路由写错的问题，修正后复跑通过，详见「验证」中的 e2e 记录。

## 做了什么

1. **Playwright 基座**：新增 `pet-lumina-app/playwright.config.ts`，固定单 worker 串行、`channel: 'msedge'`、headless、失败留 trace/screenshot；不下载额外浏览器，直接用本机 Edge。
2. **三条真实用例**：新增 `pet-lumina-app/e2e/flows.spec.ts`。用 `page.route` 拦截外部背景图等无关请求，App 用例使用 `13800001001` / `13800001002` 两个账号隔离限流计数；管理员用例复用第一条用例创建的会话。
3. **一条命令起停**：新增 `pet-lumina-app/scripts/e2e-stack.ps1`，按顺序拉起 stub_java(8080)、stub_llm(8098)、Agent(8099)、App vite(5174)、管理端 vite(3000)，健康检查后跑 Playwright，`finally` 用 `taskkill /T` + 端口兜底清理；日志写 `%TEMP%\petlumina-e2e\`。
4. **可测试选择器**：只给 App 登录/对话、管理端登录/会话列表/会话详情加 `data-testid`，没有改业务逻辑。
5. **固定桩数据**：复用现有 `backend-agent/tests/stub_java.py` 与 `stub_llm.py`；疫苗记录、引用 `7001`、管理员 token 都来自桩，不依赖真实后端与真实模型。

## 已知局限

- e2e 目前只覆盖 C9 要求的三条链路，未接入 CI；CI 仍只跑 `backend-agent` 的 lint/test/evals（C8 的剩余项）。
- 本轮未修改 `backend/`（Java），因此未重跑 `mvn test`；改动集中在 App、管理端测试选择器与 e2e 资产。
- 本机管理端 `npm run build` 需要把 `TEMP/TMP/ESBUILD_TMPDIR` 指向仓库内目录，属于环境绕行，不是代码修复；换机器/CI 前需要确认该问题是否仍存在。
- 依赖本机已安装的 Edge（`channel: 'msedge'`）；没有 Edge 的环境需要安装浏览器或调整 channel。
- 429 用例依赖 Agent 以 `PET_AGENT_RATE_LIMIT_PER_MINUTE=1` 启动，且三条用例串行；并发执行会污染限流窗口。
- 首次运行的管理端路由问题已修复并复跑，但如果后续管理端从 hash 路由切到 history 路由，测试路径需要同步调整。
