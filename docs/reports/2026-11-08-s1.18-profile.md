## 4. 真实缺陷与修复

| # | 现象 | 根因 | 修法 |
| --- | --- | --- | --- |
| D1 | 第一次真机画像 `fact_count=0` | 画像重算与记忆写入是两个并发任务，画像先跑就查不到事实 | 删掉独立 topic，把 `rebuild` 挂进记忆消费者，因果顺序天然成立；`TOPICS` 回到 3 个 |
| D2 | `stale` 断言失败 | 内存仓储时间只到秒，画像与事实同秒不可区分 | `_now()` 改微秒精度；`is_stale` 改用 `meta.factWatermark` 比较 |
| D3 | 第二次跑 MySQL 契约测试撞唯一键 | 用例写死用户且不清理，污染真机库 | 每次生成新 `user_id`/`id`，`finally` 删除后关闭连接 |
| D4 | `ImportError: TOPIC_PROFILE_REFRESH` | 删 topic 后 `test_admin.py` 的集合断言未同步 | 同步改为三 topic |

## 5. 设计取舍

1. **不调模型**：画像若交给 LLM 生成，"同一事实两次生成不同结论"就无法验收；确定性函数让每一条结论都能回放到事实。
2. **追加式版本**：覆盖写会让"上次为什么这么说"永远查不到；保留 20 版足够 diff，又不至于无限膨胀。
3. **`stale` 而不是自动重算**：自动重算会在用户看页面的瞬间引入写放大；标记过期 + 一键重算把控制权交回人。
4. **只注入风险与待办**：整份画像进 system 会挤占上下文并诱导模型复述结构，反而降低回答质量。

## 6. 已知缺口

1. 画像只有规则聚合，没有 `routine`（作息）与行为趋势——需要日志侧聚合，属于 C2 的下一层。
2. 画像无"人工修正"入口：管理员只能看与删事实，不能纠正字段。
3. 版本历史只有列表，没有两版 diff 视图。
4. 未做画像导出（事实有导出，画像没有）。
5. `profile_snapshot` 未进 `init.sql`（与 v2.13–v2.17 一致，靠增量脚本）。
