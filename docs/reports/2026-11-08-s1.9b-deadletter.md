### 3.3 启动补偿（崩溃不丢任务）

模拟"进程崩在消费中途"：往 `pet:task:agent.audit.tool:processing` 塞一条消息后重启服务。

```
{"logger":"agent.task","msg":"task inflight recovered","topic":"agent.audit.tool","moved":1}
{"logger":"agent.task","msg":"task inflight recovered on startup","recovered":1}
tool_call_log: (9123456789012345678, 'get_pet_profile', 1, 7)
processing len: 0 ; main len: 0
```

即：启动时先搬回在途消息，再开消费，最终落库且队列干净。

## 5. 设计决策

1. **启动补偿必须在消费者之前**：反了会与 consumer 抢同一条消息（`lifespan` 里有注释，改顺序要先读）。
2. **重放要重置 `attempt`**：否则"失败一次 → 立刻回死信"，重放等于没放。
3. **死信不做自动无限重试**：只提供"看得见 + 手动放回"，避免故障时形成忙循环。
4. **接口默认 fail-safe**：`TASK_BACKEND=off` 时接口返回 `enabled=false` 而不是 404/500，运维一眼能分辨"没开"与"坏了"。
5. **权限沿用 S1.7 的口径**：`role` 只来自 Java `/auth/current`，管理端读/写都留 `admin.access`。

## 6. 已知缺口（未做，不算完成）

- RocketMQ 实现（S1.9-b 的"真正的 MQ"）——本机无 broker，需 Docker 或独立部署，属 S1.9-c。
- 死信批量重放（当前一次最多 100 条、单个 topic）。
- 队列深度的历史曲线与告警（只有瞬时值）。
- `recover` 只在启动时跑一次；长时间运行中的 processing 泄漏（消费者卡死）仍需 `XAUTOCLAIM` 式的定期扫描。
- 多副本下两个进程同时 `replay_dead_letter` 的并发控制（当前依赖 Redis 单命令原子性，未做互斥）。
