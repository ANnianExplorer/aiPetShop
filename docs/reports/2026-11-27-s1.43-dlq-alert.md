## 1. 目标与边界

B4 的退避、死信、自动重投此前已交付，唯一尾巴是「死信超阈值打 WARN / 接告警通道」。本轮把它做成可运维的闭环：

1. 死信数达到阈值时打结构化 WARNING；
2. 同一段越线只告警一次，回落后再越线可重新告警（边沿触发，避免每轮巡检刷屏）；
3. 计数必须包含无法解析的坏 payload——旧实现 `len(dead_letters())` 会跳过坏数据，管理端与告警都会漏计；
4. 告警信号进 `/metrics`，由 Prometheus/Alertmanager 接走，不引入 webhook 依赖与密钥。

### 3.5 过程中的失败与修正（如实记录）

首轮定向测试是 `31 passed + 2 failed`。失败不是产品逻辑，而是测试自己把同步 lambda 传给了异步等待器：


修正：等待条件改用 `_wait_until(lambda: len(queue._dlq.get(topic, [])) == N)`，不再对同步表达式 `await`。重跑后 52 passed，全量 334 passed + 1 skipped。该失败只影响测试写法，未改动产品代码。

## 5. 已知缺口与风险

1. **坏 payload 无法被 admin replay 清除**：重放接口需要解析消息，坏数据会一直留在死信列表，计数与告警也会持续。这是真实信号，不是误报；清理需要人工 `DEL`/工具，后续可做「丢弃坏死信」的管理端动作。
2. **多副本各自边沿**：每个副本维护自己的 `_dlq_alert_active`，同一段越线可能各打一条 WARNING；`pet_agent_dlq_alerts_total` 会按副本累加。Prometheus 侧用 `max by (topic)` 看看深度、Alertmanager 对同值告警去重即可。
3. **告警依赖巡检**：巡检关闭时无告警；这是有意的配置耦合，已写入 SPEC。
4. **测试口径**：队列单测仍以 `FakeRedis` 为主；本轮只对真实 Redis 做了计数检查，未跑真实 Redis 下的完整 worker 告警链路。真实 broker/多副本冒烟不在本轮范围。
5. **未做外部告警通道**：没有接 webhook/邮件，避免引入新依赖与密钥；`/metrics` 是告警通道的契约面。
